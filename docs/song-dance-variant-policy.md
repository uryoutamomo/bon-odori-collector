# 曲と振りバリエーションの設計方針

記録日: 2026-06-16

署名: おと（Codex）

## 背景

盆踊りでは、1つの会場に複数イベントがあるのと同じように、1つの曲にも複数の踊り方・振りのバリエーションが存在する。

例:

- ダンシング・ヒーロー: 中央区で見られる振り
- 盆ギリ恋歌: 上品なバージョン、控えめな所作の振り

ただし、振りのバリエーションが明確に問題になる曲は全体の10%から20%程度と見込む。全曲で完璧に管理しようとすると、データ整備が重くなりすぎる。

## 方針

曲マスタは増やさず、必要な曲だけに「振りバリエーション」をぶら下げる。

曲名の別名と振りの違いは混ぜない。たとえば「ダンシング・ヒーロー（中央区バージョン）」を別曲として登録すると、曲目集計・人気曲ランキング・曲 occurrence が割れるため避ける。

曲は同じ正本に寄せ、踊り方だけを任意の別情報として扱う。

## データモデル案

`DanceVariant` のような任意テーブルを用意する。

```text
DanceVariant
- id
- song_id
- display_name
- nickname
- variant_type
- confidence
- source_event_id
- source_url
- notes
```

イベントと曲の紐付け側には、任意で `dance_variant_id` を持たせる。

```text
event_song.dance_variant_id
```

未入力の場合は「振り不明」または「一般的な振り扱い」とする。

## 命名ルール

振りのバリエーションには公式名がないことが多い。盆踊ラー間の俗称が少しだけ共通化している程度のケースも多い。

そのため、無理に正式名を作らず、説明的な仮名を使う。

例:

- 表示名: 中央区で見られる振り
- 俗称: 中央区バージョン
- 種別: 地域/イベント由来
- 確度: 観測済み、俗称/観測ベース
- 根拠: YouTube URL、イベント名、年

「上品なバージョン」のような俗称は、正式名ではなく `nickname` や `notes` に置く。

## 運用ルール

全曲に振りバリエーションを入力しない。

通常曲は、振りバリエーション未入力のまま扱う。デフォルトは「不明 / 一般的な振り」とする。

振り違いが目立ち、動画紹介やイベント紹介で価値がある曲だけ登録する。

優先して登録する条件:

- 同じ曲なのにイベントごとの踊り方が明確に違う
- 動画で「このイベントではこの振り」と紹介したい
- 盆踊ラー間で俗称がある程度通じる
- YouTubeなどで根拠を残せる

登録は「曲マスタ先行」ではなく、動画紹介・イベント紹介で必要になった時点で行う。

## 実装判断

今すぐ全体設計には組み込む。ただし入力運用は例外対応にする。

つまり、データ構造としては「振りバリエーション」を受け止められるようにしておく。一方で、全曲に振りを埋める作業はしない。まずは差分が明確で、動画紹介の価値が高い曲だけを対象にする。

## 2026-06-16 実装メモ

`rdb_builders/build_bon_odori_rdb.py` の統合RDBに、振りバリエーションの受け皿を追加した。

追加テーブル:

- `dance_variants`: 曲にぶら下がる振りバリエーションの正本候補。初期状態では空でよい。
- `event_song_links`: イベントと曲の関係。任意で `dance_variant_id` を持てる。

初期運用では、YouTubeセットリストからイベント・曲が結べるものを `event_song_links` に入れ、`dance_variant_id` は空欄のままにする。

振りバリエーションは自動推測しない。動画紹介やイベント紹介で必要になったときだけ、根拠URL・イベント・俗称/説明名つきで `dance_variants` に登録する。
