# 年次イベント継承・DB運用方針

更新: 2026-06-19
署名: おと（Codex）

## 目的

盆踊りイベントDBでは、2025年と2026年の同名イベントを同一行に混ぜず、年ごとの開催回として扱う。
一方で、曲目、雰囲気、規模感、例年時期などは過去年実績を重要な根拠として使う。
この文書は、2025年/2024年/2023年などの過去年実績から2026年開催回へ何をどう継承するか、また2027年以降に毎年どう運用するかを定める。

## 基本モデル

- イベントDBの1行は、原則として「年ごとの開催回」を表す。
- 2025年と2026年の同名イベントは、同じイベント系列に属しても別開催回として扱う。
- 年別専用テーブルや `2025開催日` / `2026開催日` のような年別カラムは増やさない。
- 年次関係は `event_year`、`series_key`、`inherited_from_year`、根拠URL、確からしさで表現する。
- 将来的に必要になったら、恒久情報を持つ `event_series` と、年次開催回を持つ `events` に分ける。

### 会場・イベント系列・年次開催回

年次データは会場ではなく、イベント系列に紐づく「年次開催回」に持たせる。

- `venues`: 場所のマスタ。住所、区、緯度経度、アクセスなど、年で変わりにくい情報を持つ。
- `event_series`: 毎年続く同じイベントの系列。代表名、通常会場、主催、別名、再開催規則を持つ。
- `event_occurrences`: その年に実際に開かれた開催回。年、日付、曜日、実際の会場、ステータス、根拠、確度を持つ。
- `occurrence_songs`: その年次開催回で観測・告知された曲目。曲名、根拠URL、観測年、確度、動画数などを持つ。

理由:

- 同じ会場で複数の盆踊り・夏祭りが行われることがあるため、会場に年次日付を直接持たせると、どのイベントの日付か分からなくなる。
- イベント系列は年によって会場が変わることがあるため、通常会場は `event_series.usual_venue_id`、実際の会場は `event_occurrences.venue_id` として分ける。
- 曲目はイベント系列の性格を示すが、年によって差し替わるため、まずは年次開催回に紐づけて保存する。

## 継承の考え方

2025年から2026年への継承は、過去年情報を2026年の確定情報としてコピーすることではない。
過去年実績を、2026年開催回に対する「根拠付きの推定・参考情報」として参照する。

- 2025年イベント: 過去実績。
- 2026年イベント: 今年の開催回。
- 2026年の不足情報: 2025年/2024年/2023年などの過去年実績から推定し、根拠と確からしさを付ける。

継承された情報には、必ず以下のような根拠ラベルを残す。

- `source_year`: 根拠になった年。
- `source_event_id`: 根拠になったイベント。
- `source_url`: 根拠URL。
- `basis`: `past_evidence` / `past_observed` / `past_announcement` / `series_profile` など。
- `basis_label`: `2025年実測`、`2024年告知`、`過去実績` など。
- `confidence`: `inherited`、`hint`、`predicted`、`confirmed` など。

## 情報種別ごとの扱い

### 開催日

- 過去年の開催日を翌年へ直接コピーしない。
- 2025年/2024年/2023年などの開催日は、2026年の「例年時期」「開催可能性」「探索優先度」のヒントとして使う。
- 2026年の開催日は、公式HP、自治体/主催発表、信頼できるX投稿などで確認できたときに昇格する。
- 日付が未確認の間は、開催日欄を空欄または未確認扱いにし、別途「例年時期」や「月/旬ヒント」として保持する。

### 固定日開催

「毎年8月1日・2日」のように曜日ではなく月日で固定されているイベントは、自由文メモだけに置かず、イベントDBに機械判定できる固定日カラムを持たせる。

推奨カラム:

- `開催パターン種別`: `固定日`
- `固定日開始月`: number
- `固定日開始日`: number
- `固定日終了月`: number
- `固定日終了日`: number
- `固定日根拠URL`: url

運用:

- 固定日カラムがある場合は、同曜日スライドより固定日を優先して翌年候補を作る。
- 固定日カラムは「今年確認済み」ではなく「例年規則」の根拠なので、今年の公式告知が出るまでは未確認表示を維持する。
- 自由文の `開催パターン詳細` には、なぜ固定日と判断したかを `[fixed_date_rule]` として短く残す。
- 2026-06-20時点の初期登録対象は、花園神社 盆踊り（毎年8/1〜8/2）と山王音頭と民踊大会（毎年6/13〜6/15）。

### 曲目

- 過去実績を2026年の曲目予測に使ってよい。
- ただし、2026年公式曲目表、2026年事前告知、2026年実測があればそれらを優先する。
- YouTubeなどの2025年実測は、`2025年実測` という根拠ラベルと減衰付き確率で使う。
- 曲目候補は「2026年確定曲」と「過去実績からの予測曲」を分けて表示・保存する。

### 雰囲気・規模感・曲の傾向

- 雰囲気、規模感、屋台、混雑感、曲の傾向、地域色は、イベント系列に近い情報として継承してよい。
- ただし、根拠年、根拠URL、観測元、確からしさを残す。
- 今年の投稿や動画が出たら、過去年由来の参考情報を今年実測で補強または更新する。

### 開催可能性

- 過去年開催実績は「今年もある可能性」の根拠になるが、開催確定ではない。
- 公式HP、主催SNS、自治体情報、信頼できるX告知が出た場合に、開催可能性を上げる。
- 単独の弱い投稿や過去年実績だけで「確認済み」にしない。

## 公開日程ステータス分類

公開サイトでは、「今年の開催日が確定しているか」と「未確認情報の根拠が何か」を分ける。
詳細な運用手順は `docs/public-schedule-status-manual.md` を正とする。

正規カテゴリ:

- `current_confirmed_upcoming`: 今年の日付が確定し、これから開催。
- `current_confirmed_ended`: 今年の日付が確定し、すでに終了。
- `historical_reference`: 2025年/2024年/2023年などの過去年開催実績があるが、今年の日付は未確認。
- `schedule_hint_only`: 月・旬・会場メモなどの時期ヒントはあるが、具体的な過去年開催日はない。
- `date_unknown`: 日程情報がほぼない。

運用上の注意:

- `recurring_last_year` や `last_year` は新しい正規カテゴリ名にしない。
- 既存コードの `recurring_last_year` は移行前の暫定名で、意味は `historical_reference` と同じ「過去実績あり・今年未確認」。
- 継続性スコアは `historical_reference` の補助情報であり、開催確定の根拠ではない。
- 過去年実績は `historical_occurrences`、`latest_seen_year`、`evidence_years`、`continuity_score` として保持する。

## 情報源ごとの時間的役割

### YouTube

- 基本的に過去イベントの実績証拠として扱う。
- 曲目、雰囲気、規模感、実際の開催有無の根拠として強い。
- 未来イベントの開催日や開催確定の直接証拠としては扱わない。
- 2025年YouTubeは、2026年の「過去実績による予測」の根拠として使う。
- 2024年・2023年などのYouTubeも同じく過去実績として扱い、今年の開催確定には使わない。

### 公式HP・自治体/主催情報

- 未来または今年のイベント情報の最優先証拠として扱う。
- 開催日、場所、主催、公式曲目、開催確定の判断ではYouTubeより優先する。

### X

- 未来イベントの告知、参加予定、現地兆候、当日/事後の実測情報として扱う。
- 信頼度は投稿者、内容、複数ソース有無で評価する。
- 主催・自治体・会場・信頼済みアカウントの投稿は、通常の個人投稿より強い根拠とする。

## 2026年初年度の特別運用

2026年は初年度運用なので、通常の冬ロールオーバーではなく、2026年6月中に一度だけ2025年から2026年への継承バッチを行う。

手順:

1. 2025年イベントを `event_name + venue` を基本に系列化し、`series_key` を付ける。
2. 既に2026年開催回があるものは、その2026イベントに同じ `series_key` を付ける。
3. 2026年開催回がないが継承対象にするものは、2026年の未確認/継承候補として作成する。
4. 開催日はコピーせず、例年時期・月・旬のヒントだけを継承する。
5. 曲目、雰囲気、規模感、曲の傾向は、根拠年と確からしさ付きで継承する。
6. 2026年公式情報や信頼できるX情報が見つかったものから、未確認/継承候補を確認済みへ昇格する。
7. YouTube由来の2025年情報は、2026年の確定情報ではなく、過去実績による予測根拠として扱う。

## 過去年データ収集方針

2026年の未確認イベントに「使える日付目安」を出すため、2025年単年だけでなく、最低3年分の実績を集めてイベント系列ごとの開催規則を推定する。

- 最低ライン: 2023年、2024年、2025年の3年分。
- 理想: 重要イベントについては2019年、2022年、2023年、2024年、2025年など5年分相当。
- 2020年、2021年はコロナ影響で欠測・例外年として扱う可能性が高い。
- 最終的には、2024年と2023年も2025年と同程度の粒度で収集することを目標にする。

収集対象:

- 開催日、開始日、終了日、曜日。
- 会場、イベント名、別名。
- 根拠URL、動画URL、投稿URL、公式/非公式の種別。
- 曲目。曲はまず直近2年分を優先して集める。

曲目を2年分から始める理由:

- 曲は毎年完全一致ではなく、「定番曲 + その年の差し替え」になりやすい。
- 2年続けて出た曲は定番候補として扱える。
- 片年だけの曲は年替わり候補またはその年の特色として扱う。

開催規則の推定例:

- `7月第4金土`
- `8月第1土日`
- `海の日の前後`
- `お盆前の金土`
- `例大祭の宵宮`
- `学校夏休み開始直後の土日`

予測ラベル:

- 3年以上の実績から規則が一致: `高精度予測`
- 2年実績が一致: `有力予測`
- 1年のみ: `直近年実績ベース`
- 実績が不一致または月しか分からない: `時期目安`

サイト表示では、予測と確定を混ぜない。

例:

```text
7/24〜7/25ごろ
過去3年の開催規則から予測・今年未確認
```

## 2027年以降の通常運用

毎年冬に、当年実績と過去年実績から翌年開催回候補を生成する。

- 10月から11月: 当年の実績、曲目、雰囲気、証拠を整理する。
- 12月から1月: 当年実績から翌年開催回候補を生成する。
- 2月から5月: 公式HP、自治体情報、主催SNS、Xで裏取りする。
- 6月から9月: 今年情報で開催日、曲目、ステータス、証拠を更新する。
- シーズン後: 今年のYouTubeやXを実績証拠として整理し、翌年継承の材料にする。

## ステータス運用

- `継承候補`: 当年実績または過去年実績から翌年候補として作った段階。
- `未確認`: 今年開催の可能性はあるが、今年の直接証拠が弱い段階。
- `確認済み`: 公式HP、自治体/主催発表、信頼できる今年情報で開催日または開催が確認できた段階。
- `終了`: 当年開催が終了し、実績として扱う段階。
- `保留`: 盆踊り本DB対象か、年、会場、公式確認などに不確実性が残る段階。
- `対象外`: 周辺イベント、全国候補、盆踊りでないイベントなど、本DB登録対象外の段階。

## 実装上の推奨

- まずは既存 `events` を年次開催回テーブルとして明確に使う。
- 必要に応じて `event_year`、`series_key`、`inherited_from_year` を追加する。
- 継承結果は直接Notionへ大量反映せず、まずdry-run JSON/MDに出す。
- dry-runで、作成候補、既存2026イベントへの紐付け候補、保留、対象外を分ける。
- Notion反映は既存apply系スクリプトに寄せ、根拠と差分が追える形にする。
- RDBでは、証拠ごとに `evidence_year` と `evidence_role` を持つ方針にする。

`evidence_role` の例:

- `past_result`: YouTubeなどの過去実績。
- `future_announcement`: 公式HPや主催投稿などの未来告知。
- `current_hint`: 今年の弱いヒント。
- `current_result`: 今年の事後実測。

## 判断優先順位

開催日:

1. 公式HP、自治体、主催発表。
2. 主催/会場/信頼済みXの今年告知。
3. 複数の独立した今年情報。
4. 過去実績による例年時期ヒント。

曲目:

1. 今年の公式曲目表。
2. 今年の事前告知。
3. 今年のYouTube/投稿による実測。
4. 過去年YouTube/投稿による実績予測。

雰囲気:

1. 今年の投稿/動画。
2. 過去年の投稿/動画。
3. 会場・系列の一般情報。

## 注意

- 継承情報を確定情報に見せない。
- YouTubeに動画があることを、今年開催確定の根拠にしない。
- 開催日を過去年から機械変換しない。
- 年ごとのカラムを増やしてスキーマを固定年に依存させない。
- Notion正本を壊さないため、継承バッチは必ずdry-runを挟む。
