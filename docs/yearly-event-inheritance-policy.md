# 年次イベント継承・DB運用方針

更新: 2026-06-16
署名: おと（Codex）

## 目的

盆踊りイベントDBでは、2025年と2026年の同名イベントを同一行に混ぜず、年ごとの開催回として扱う。
一方で、曲目、雰囲気、規模感、例年時期などは前年実績を重要な根拠として使う。
この文書は、2025年実績から2026年開催回へ何をどう継承するか、また2027年以降に毎年どう運用するかを定める。

## 基本モデル

- イベントDBの1行は、原則として「年ごとの開催回」を表す。
- 2025年と2026年の同名イベントは、同じイベント系列に属しても別開催回として扱う。
- 年別専用テーブルや `2025開催日` / `2026開催日` のような年別カラムは増やさない。
- 年次関係は `event_year`、`series_key`、`inherited_from_year`、根拠URL、確からしさで表現する。
- 将来的に必要になったら、恒久情報を持つ `event_series` と、年次開催回を持つ `events` に分ける。

## 継承の考え方

2025年から2026年への継承は、前年情報を2026年の確定情報としてコピーすることではない。
前年実績を、2026年開催回に対する「根拠付きの推定・参考情報」として参照する。

- 2025年イベント: 過去実績。
- 2026年イベント: 今年の開催回。
- 2026年の不足情報: 2025年実績から推定し、根拠と確からしさを付ける。

継承された情報には、必ず以下のような根拠ラベルを残す。

- `source_year`: 根拠になった年。
- `source_event_id`: 根拠になったイベント。
- `source_url`: 根拠URL。
- `basis`: `past_evidence` / `past_observed` / `past_announcement` / `series_profile` など。
- `basis_label`: `2025年実測`、`2025年告知`、`前年実績` など。
- `confidence`: `inherited`、`hint`、`predicted`、`confirmed` など。

## 情報種別ごとの扱い

### 開催日

- 前年の開催日を翌年へ直接コピーしない。
- 2025年の開催日は、2026年の「例年時期」「開催可能性」「探索優先度」のヒントとして使う。
- 2026年の開催日は、公式HP、自治体/主催発表、信頼できるX投稿などで確認できたときに昇格する。
- 日付が未確認の間は、開催日欄を空欄または未確認扱いにし、別途「例年時期」や「月/旬ヒント」として保持する。

### 曲目

- 前年実績を2026年の曲目予測に使ってよい。
- ただし、2026年公式曲目表、2026年事前告知、2026年実測があればそれらを優先する。
- YouTubeなどの2025年実測は、`2025年実測` という根拠ラベルと減衰付き確率で使う。
- 曲目候補は「2026年確定曲」と「前年実績からの予測曲」を分けて表示・保存する。

### 雰囲気・規模感・曲の傾向

- 雰囲気、規模感、屋台、混雑感、曲の傾向、地域色は、イベント系列に近い情報として継承してよい。
- ただし、根拠年、根拠URL、観測元、確からしさを残す。
- 今年の投稿や動画が出たら、前年由来の参考情報を今年実測で補強または更新する。

### 開催可能性

- 前年開催実績は「今年もある可能性」の根拠になるが、開催確定ではない。
- 公式HP、主催SNS、自治体情報、信頼できるX告知が出た場合に、開催可能性を上げる。
- 単独の弱い投稿や前年実績だけで「確認済み」にしない。

## 情報源ごとの時間的役割

### YouTube

- 基本的に過去イベントの実績証拠として扱う。
- 曲目、雰囲気、規模感、実際の開催有無の根拠として強い。
- 未来イベントの開催日や開催確定の直接証拠としては扱わない。
- 2025年YouTubeは、2026年の「前年実績による予測」の根拠として使う。

### 公式HP・自治体/主催情報

- 未来または今年のイベント情報の最優先証拠として扱う。
- 開催日、場所、主催、公式曲目、開催確定の判断ではYouTubeより優先する。

### X

- 未来イベントの告知、参加予定、現地兆候、当日/事後の実測情報として扱う。
- 信頼度は投稿者、内容、複数ソース有無で評価する。
- 主催・自治体・会場・信頼済みアカウントの投稿は、通常の個人投稿より強い根拠とする。

## 2026年初年度の特別運用

2026年は初年度運用なので、通常の冬ロールオーバーではなく、2026年6月中に一度だけ2025年から2026年への継承バッチを行う。

手順:

1. 2025年イベントを `event_name + venue` を基本に系列化し、`series_key` を付ける。
2. 既に2026年開催回があるものは、その2026イベントに同じ `series_key` を付ける。
3. 2026年開催回がないが継承対象にするものは、2026年の未確認/継承候補として作成する。
4. 開催日はコピーせず、例年時期・月・旬のヒントだけを継承する。
5. 曲目、雰囲気、規模感、曲の傾向は、根拠年と確からしさ付きで継承する。
6. 2026年公式情報や信頼できるX情報が見つかったものから、未確認/継承候補を確認済みへ昇格する。
7. YouTube由来の2025年情報は、2026年の確定情報ではなく、前年実績による予測根拠として扱う。

## 2027年以降の通常運用

毎年冬に、前年実績から翌年開催回候補を生成する。

- 10月から11月: 当年の実績、曲目、雰囲気、証拠を整理する。
- 12月から1月: 当年実績から翌年開催回候補を生成する。
- 2月から5月: 公式HP、自治体情報、主催SNS、Xで裏取りする。
- 6月から9月: 今年情報で開催日、曲目、ステータス、証拠を更新する。
- シーズン後: 今年のYouTubeやXを実績証拠として整理し、翌年継承の材料にする。

## ステータス運用

- `継承候補`: 前年実績から翌年候補として作った段階。
- `未確認`: 今年開催の可能性はあるが、今年の直接証拠が弱い段階。
- `確認済み`: 公式HP、自治体/主催発表、信頼できる今年情報で開催日または開催が確認できた段階。
- `終了`: 当年開催が終了し、実績として扱う段階。
- `保留`: 盆踊り本DB対象か、年、会場、公式確認などに不確実性が残る段階。
- `対象外`: 周辺イベント、全国候補、盆踊りでないイベントなど、本DB登録対象外の段階。

## 実装上の推奨

- まずは既存 `events` を年次開催回テーブルとして明確に使う。
- 必要に応じて `event_year`、`series_key`、`inherited_from_year` を追加する。
- 継承結果は直接Notionへ大量反映せず、まずdry-run JSON/MDに出す。
- dry-runで、作成候補、既存2026イベントへの紐付け候補、保留、対象外を分ける。
- Notion反映は既存apply系スクリプトに寄せ、根拠と差分が追える形にする。
- RDBでは、証拠ごとに `evidence_year` と `evidence_role` を持つ方針にする。

`evidence_role` の例:

- `past_result`: YouTubeなどの過去実績。
- `future_announcement`: 公式HPや主催投稿などの未来告知。
- `current_hint`: 今年の弱いヒント。
- `current_result`: 今年の事後実測。

## 判断優先順位

開催日:

1. 公式HP、自治体、主催発表。
2. 主催/会場/信頼済みXの今年告知。
3. 複数の独立した今年情報。
4. 前年実績による例年時期ヒント。

曲目:

1. 今年の公式曲目表。
2. 今年の事前告知。
3. 今年のYouTube/投稿による実測。
4. 前年YouTube/投稿による実績予測。

雰囲気:

1. 今年の投稿/動画。
2. 前年の投稿/動画。
3. 会場・系列の一般情報。

## 注意

- 継承情報を確定情報に見せない。
- YouTubeに動画があることを、今年開催確定の根拠にしない。
- 開催日を前年から機械変換しない。
- 年ごとのカラムを増やしてスキーマを固定年に依存させない。
- Notion正本を壊さないため、継承バッチは必ずdry-runを挟む。
