# 意味判定層の退場：現況の実測（2026-08-16）

2026-08-08 の設計方針転換で「Pythonで自動化するのは定期的で定型的な情報収集のみ。解釈は基本的におとやことがやりたい」と決まり、
その本体である**意味判定層の退場**は 8/15 の棚卸しで「7本merge して純増6,051行、シンプル化はまだ1行も起きていない」と指摘された。

着手にあたって現況を実測したところ、**8/8 に立てた計画（静的名簿化→AI影運用→旧consumer遮断→実績台帳）が
そのままでは進められない**ことが分かった。前提が3つ変わっている。この文書はその記録である。

## 実測の方法

`.github/workflows/*.yml` の `run:` から起動される `.py` を入口とし、import を再帰的に辿って到達集合を作った
（スクリプトは使い捨てで、結果だけをここに残す）。「意味判定」は、日本語の語彙リストと日本語を含む正規表現で
「これは何か」を決めている箇所として数えた。

| 対象 | 実測 |
|---|---|
| 全Python（tests除く） | 456本 / 111,598行 |
| 日次から到達 | 105本 / 32,770行 |
| 到達しない（孤立） | 351本 / 78,828行（70%） |
| 到達分のうち日本語の語彙・正規表現を持つ | 70本 |

**孤立70%は「消せる70%」ではない。** E0/J0/E2 の本体（`review_inbox_adapters/` 1,958行）や反映層（`report_apply/` 2,476行）は
**手動運用で使うもの**で、workflow から呼ばれないだけである。名前どおり退場候補と言えるのは `legacy/`（153本 32,541行）だが、
テストが10本以上 import しているので、消すならテストごと消す判断が要る。

## 変わっていた前提1：「捨てる」意味判定はもう退場済み

8/15 の INV-COL-005（収集の関門は意味を理由に投稿を捨てない）で、除外語による打ち切り・🔴ノイズ判定・
証拠分類の除外語減点はすべて廃止されている。いま収集入口で落ちるのは `no_context`（文脈信号が1つも無い）だけで、
これは意味を読まずに判定できる条件として仕様が明示的に許しているものである。

**つまり「LLMが読むべきものをPythonが捨てている」という当初の問題は、すでに解けている。**

## 変わっていた前提2：残る意味判定は「捨てる」ではなく「順位づけ」

いま生きている意味判定の出力先を辿ると、次の4つに使われていた。

- **タグ付け** — `_score_voice` の🟢一次レポ/🟡関心、`_x_post_value_score` の📅未来予定/📌予定候補
- **アカウント評価** — `_build_x_account_scores`、`review_x_candidate_posts.py`、証拠RDB（`rdb_builders/build_evidence_rdb.py`）
- **会場検知** — `detect_venues_for_queue` が `value_score >= 7` を条件にしている
- **証拠分類** — `collection_support/event_evidence.py` の `classify_event_evidence`（564行・和文正規表現16箇所）

どれも情報を捨ててはいないが、**下流が実際に消費している**。特にアカウント評価は 8/13 に2軸スコアへ作り直したばかりで、
ここを先に触ると盆踊ラー選抜が静かに壊れる。**単独で消せるものは1つも無かった。**

## 変わっていた前提3：E0/E2 は X投稿経路の代わりにならない

これがいちばん大きい。E0（`build_event_inbox_candidates.py`）の入力は
`data/official_notice_reports/` と `data/firsthand_reports/` で、**ことが掲示物やポスターを読んで手で書き出したレポート**である。
X投稿から自動生成されるものではない。

いまリポジトリには2本の系統が並んでいる。

- **掲示物の系統**（新）— 人が読む → レポート → E0 → J0 → E2 → master RDB。LLM判定が入っている
- **X投稿の系統**（旧）— 収集 → 意味判定（`_x_post_value_score` / `classify_event_evidence`）→ `build_x_gap_candidates.py` → review_inbox（判断待ち561件）

**新しい系統は掲示物にしか繋がっていない。** だから旧経路の意味判定を切っても、代わりが受け止めない。
E0/E2 は日次workflowから参照ゼロだが、それは「組み込み忘れ」ではなく、そもそも日次で増える入力を持っていないからである。

## 退場の順序（実態に合わせた書き直し）

上を踏まえると、必要な段は5つで、**8/8 の計画には第0段が抜けていた**。

0. **X投稿から「提案」を作る器**（新規）— E0 の入力形式（`official_notice` レポート相当）を、X投稿から組み立てる。
   ここで意味は判断せず、投稿とその素材を提案の形に整えるだけにする
1. **粗い間引き**（意味を見ない条件のみ）— 既見URL・完全重複・リツイート・構造化areaで明らかに23区外。
   内田さんの折衷案（500→100件）がこれにあたる。**流量を先に決める**（合意事項2。決めないと561件の再演）
2. **LLM判定**（E2 の枠組みを再利用）— 聞くのは同一性など1問だけにする。変更型は機械が決める（E2の成功形）
3. **影運用** — 旧経路と並走させ、旧が拾って新が落としたものを数える。ここで初めて「捨てても大丈夫か」が測れる
4. **旧consumer遮断 → 削除** — タグ・アカウント評価・会場検知の消費先を新経路へ移してから、意味判定コードを消す

**行数が実際に減るのは第4段だけである。** 第0〜3段はむしろ増える。
「シンプル化が1行も起きていない」状態は、少なくとももう1段は続く。これは正直に見込んでおく。

## 次に決めるべきこと（内田さんの判断）

1. **第0段の器を作るか、それとも X投稿経路は当面いまのままにするか。** 意味判定は情報を捨てなくなったので、
   いま残っているのは順位づけであり、**害は「Pythonが解釈している」という設計上の不整合に留まっている**。
   急いで消す実害が無いなら、先に別の宿題（費用削減の③、区の穴埋め）を優先する選択もある
2. **`legacy/` 153本 32,541行を消すか。** 意味判定層の退場とは別テーマだが、行数としては最大。
   テスト10本以上が import しているので、テストごと消す判断が要る
