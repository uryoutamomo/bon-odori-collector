# E0X: X投稿から E0 レポートを作る器（意味判定層の退場・第0段）v1.3

作成: 2026-08-16 / こと（Claude Code）／内田さん承認済み（2026-08-16「おとに実装を依頼してください」）
v1.1（2026-08-16）＝おとの仕様レビューで出た3件の穴を埋めた。**stateの2段階化（§5）／日付の正規化規則と
過去日の除外（§3・§5・§7）／束ねの代表を初回固定に修正（§8）**。いずれも v1.0 では未定義または誤りだった。
上位の設計＝ローカル判断統一（E0 → J0 → E2）。この文書はその**入口をX投稿へ広げる**ための仕様である。

## 0. コンセプト（設計判断に迷ったらここへ戻る）

内田さんの言葉＝「LLMの誤りは人間とほぼ同等。ただしLLMは全体像を見渡すことを見落としがち。
だからLLMの一つ一つの業務はシンプルであるべきで、全体を見渡すのは別のシーンかつ別のモデルで行う」。

E2はこれに従って「LLMに聞くのは同一性3つだけ、変更型は機械が決める」形にして成功した。
**E0Xも同じ形をとる。LLMに聞くのは「読んで点数を付け、開催情報なら書き写す」ことだけで、
既存イベントとの照合（同一性）は一切させない。それはE2の仕事である。**

## 1. 実測（この仕様の前提）

### 1.1 2026-08-15 の採点実験の集計（2026-08-16 に こと が集計）

おとが400件を採点した結果を、パケット側の `gate_passed` と突き合わせた。母集団は 8/15 収集の生投稿1,388件、
関門通過1,098件・落選290件。標本400件は通過319・落選81で母集団と同じ比率。

- **関門（`no_context`）で落ちた81件は、採点が全件1点（無関係）だった。** 4点以上0件、3点0件。
  つまり「LLMが読むべきものをPythonが捨てている」という 8/8 の問題意識は、実データでも解けている。
  ただし81件で0件は「ほぼゼロ」であって「絶対にゼロ」ではない（1%混在なら標本では0〜1件しか出ない規模）
- **通過319件のうち104件（33%）が1点。** 母集団換算で1日約358件の無関係な投稿が下流へ流れている
- **5点（開催情報そのもの）は標本84件＝母集団換算291件/日**

### 1.2 出口の細さ（これが第0段を作る理由）

`build_x_gap_candidates.py` が下流へ出しているのは **日次30件が上限**
（`OFFICIAL_NEW_EVENT_CAP=5` / `INFORMAL_NEW_EVENT_CAP=10` / `PAST_EVENT_REPORT_CAP=10`／全体 `--limit 30`）。
**開催情報291件/日が入口を通っているのに、30件しか外に出ていない。**
実物には「六中納涼盆踊り大会2026 8/22（土）19時から 北小岩小学校校庭」（江戸川区・私人投稿）のような、
そのまま登録できる告知が含まれていた。

### 1.3 間引きは効かない（8/15 と 8/16 の両方で確認）

意味を見ない条件（リツイート・完全重複・既見URL・構造化areaで23区外）はほとんど効かない。
リツイートは収集時点で除外済みで0件、完全重複は日15件程度、**`area`/`region` フィールドはX投稿に1件も無い**
（10,764件中0件）。8/15 の実測でも「重複と多投アカウントを落として1,388→1,327件」で1割も減らなかった。
**だから量は絞らず、LLMが全部読む前提で設計する。**

### 1.4 作業量（おとの実測・2026-08-15）

400件を1パケットで採点でき、「一括でも可能だが本文量の確認負荷が高い。日次1,388件は4〜5パケット
（約280〜350件）が現実的」との回答。**この見積もりをそのまま採用する。**

## 2. 目的

**入口を通っている開催情報を、Pythonの選別ルールではなくLLMの読み取りで提案に変える。**
実質的な中身は、旧経路の日次30件上限を外すことである。当初「捨てられたものを救う器」として
設計していたが、§1.1 のとおり救うものが無かったので目的を置き直した。

## 3. 範囲

**v1で扱う**＝日次のX投稿全件（`voices.json` のX系ソース）を読み、
**これから開催される盆踊り等の行事の告知から開催情報を取り出す**。公式・私人を問わない（§9 の出典の扱いで区別する）。

**v1で扱わない**＝**過去日の開催報告**（下記）、曲目の抽出（別経路）、中止・延期の検知（旧経路が担当を続ける）、
既存イベントとの照合（E2の仕事）、`.github/workflows/` への組み込み（手動で回して実測してから）。

**過去日を外す理由（2026-08-16 おとの指摘で明確化）**＝E0 の `_expires()` は `date_end`（無ければ `date_start`）基準で、
取り込み時点で過ぎている提案は `expired` として候補化されない。過去日のレポートを作っても E0 が必ず捨てるので、
作るだけ無駄になる。**採点は全件に付ける**（5点でも過去日ならレポートを作らないだけ）ので、
過去の開催報告を扱いたくなったときは記録から拾い直せる。

## 4. 全体の流れ

```
voices.json ──[形式フィルタ]──→ パケット（280〜350件×4） ──[LLMが読む]──→ 回答JSON
                                                                              │
                                                                    [機械が本文と照合]
                                                                              ↓
                                                    data/x_post_reports/*.json（official_notice形式）
                                                                              ↓
                                                        既存のE0 → J0 → E2 → master RDB
```

**E0 には一切手を入れない。** 生成するレポートを既存の `official_notice` 形式そのままにし、
`notice_kind: "x_post"` で由来を区別する。E0 の `_report_entries` は `source.report_id` /
`source.raw_text` / `events` しか要求しないので、そのまま通る。新しい判定層も新しい契約domainも作らない。

## 5. パケット生成（`build_x_extraction_packets.py`）

### 形式フィルタ（意味を見ない条件だけ。語彙リストを使わない）

1. `source` が X 系（`x` / `x_whitelist` / `x_proactive` / `x_event_history`）
2. **投稿日が `--since`（既定＝前日）以降であること。** 投稿日が読めないものは落とさず通す
3. `data/x_extraction_state.json` で**処理済み**の `tweet_id` は除く（下記）
4. 本文の正規化（URL除去・空白除去）が同一のものは1件だけ残す。
   **この重複判定は state の判定より先に行う**——処理済みの投稿と本文が同じ投稿は、
   別の `tweet_id` でもパケットに出さない（同じ本文なら読み直しても同じ結果になるため。
   毎日同じ告知を流すアカウントを何度も読まずに済む）

### ★ 投稿日の下限と1回あたりの上限（v1.3 で追加。実データで通して見つかった穴）

**`voices.json` は日次の差分ではなく累積である。** 2026-08-16 時点で X 系だけで 32,476件あり、
state が空の初回実行では **102バッチ／30,557件**が対象になる。1バッチ300件として102回の判定が要る計算で、
現実的でない。仕様v1.2 まではここに条件を置いていなかった（**こちらの書き落とし**。テストは全部緑だった）。

- `--since`（既定＝**前日**）以降に投稿されたものだけを対象にする。実測で **3バッチ／778件**になり、
  おとの「1バッチ280〜350件が現実的」と一致する
- `--max-batches`（既定10）で1回に出すバッチ数を制限する。**超えた分は捨てない**——
  `issued_at` を書かないので次回そのまま出てくる
- 過去へ遡りたいときだけ `--since 2026-07-01` のように明示する。それでも上限で頭打ちになる

**日付や盆踊り語での絞り込みはしない。** §1.3 のとおり間引きは効かず、内田さんの判断は「ぜんぶLLMに見せる」である。

### state は2段階で記録する（2026-08-16 おとの指摘で追加）

1段階だけだと穴が開く。apply 時にしか記録しないと**回答待ちの間に再buildして同じ投稿が別バッチへ二重に出る**し、
build 時にしか記録しないと**回答が来なかった投稿を二度と読まなくなる**。だから出したことと処理したことを分けて持つ。

`data/x_extraction_state.json` は `tweet_id` をキーに `{issued_at, batch_id, applied_at, outcome}` を持つ。

- **build時**＝出した投稿に `issued_at` と `batch_id` を書く（`applied_at` は null）
- **apply時**＝そのバッチの全packetに `applied_at` と `outcome` を書く。
  `outcome` は `report`（レポートを作った）／`scored_only`（5点未満、または5点だが過去日）／`issue`（検証で落ちた）
- **次のbuildが除外するのは `applied_at` を持つものだけ。**
  ただし `issued_at` から24時間以内で未処理のものは、既に出したばかりなので出さない
  （回答が来ないまま翌日になれば自然に再度出る＝取りこぼさない）
- `--reissue` で `issued_at` の抑止を無視できる（バッチを作り直したいとき用）

**`issue` も `scored_only` も処理済みに含める。** 同じ回答をもう一度もらっても同じ結果になるだけで、
検証で落ちたものは人が見る対象であって再試行の対象ではない。落ちた内容は取り込みレポートに残す。

**二重に出てしまった場合も害はない。** report_id が提案の中身から決まる（§8）ので、両方に回答が来てもレポートは1本になる。

### `machine_extracted_dates` の作り方（2026-08-16 おとの指摘で明確化）

**既存の日付抽出器を再利用する**（`build_x_gap_candidates.py` の `CALENDAR_DATE_RE` 相当。
「8/20」「8月20日」「2026年8月20日」を拾い、「18時」のような時刻は拾わない）。年の補完規則は次のとおり。

- 本文に年が明示されていればそれを使う
- 月日だけのときは **`posted_at` の年**で補う。ただし補った日付が**投稿月より2か月以上前**になる場合は翌年とみなす
  （8月の投稿にある「1月10日」は翌年1月。盆踊りの告知が年をまたぐのは年明けの行事だけなので、この幅で足りる）
- 1つも抽出できなければ空配列。**その投稿が5点でも、日付を伴うレポートは作らない**（§7 の `date_not_in_text` で落ちる）

### パケット形式（`data/x_extraction_packets/batch_YYYYMMDD_NN.json` と同名の `.md`）

JSONは機械可読用、mdはLLMが読む用（8/15 の採点実験と同じ二本立て）。1パケット既定300件、`--batch-size` で変更可。

```json
{"batch_id": "x_extraction_20260816_01", "generated_at": "...",
 "packets": [
   {"packet_version": 1,
    "packet_id": "<stable_id('xpacket', tweet_id, text_sha256)>",
    "no": 1,
    "tweet_id": "...", "url": "https://x.com/...",
    "account": "@...", "account_name": "...",
    "posted_at": "2026-08-15T09:00:00+00:00",
    "officiality": "<assess_source_officiality の classification>",
    "text": "投稿本文の全文",
    "has_media": true,
    "machine_extracted_dates": ["2026-08-20", "2026-08-21"]}]}
```

`machine_extracted_dates` は機械が本文から取った日付。**LLMへの参考であって答えではない**
（§7 の照合はこの集合に対して行うので、LLMが本文の日付を正しく写せば必ず通る）。

## 6. LLMに聞くこと

投稿1件につき、次の2つだけ。**既存イベントの候補集合は見せない。**

1. **点数（1〜5）** — 基準は 8/15 の `README_criteria_v1.md` をそのまま使う。
   5=開催情報そのもの／4=現地の記録／3=盆踊りの中身のある話／2=触れているだけ／1=無関係。
   **地域で減点しない**（23区外でも開催情報なら5）。**迷ったら高いほうに倒す**
2. **5点のときだけ、開催情報の書き写し** — イベント名・開催日・会場名・区、そして根拠になった本文の抜粋

### 回答形式（メッセージ本文のJSONコードブロックで返す。ファイル書き出しは求めない）

`~/.agents/` はおとのサンドボックスで read-only なので、8/15 と同じくメッセージ本文で返してもらう。

```json
{"batch_id": "x_extraction_20260816_01", "scored_by": "oto",
 "results": [
   {"no": 1, "s": 5,
    "events": [{"event_name": "第40回 ◯◯納涼盆踊り大会",
                "date_start": "2026-08-20", "date_end": "2026-08-21",
                "venue_name": "◯◯公園", "ward": "足立区",
                "quote": "8月20日・21日に◯◯公園で第40回◯◯納涼盆踊り大会を開催します"}]},
   {"no": 2, "s": 3, "n": "曲名が出ている"},
   {"no": 3, "s": 1}]}
```

`s` が点数。`n` は3点以上の短い理由（20字程度、任意）。`events` は **5点のときだけ**必須で、
1投稿に複数イベントが載ることがある（自治体アカウントが複数町会の予定をまとめて投稿する）ので配列。

## 7. 取り込みと検証（`apply_x_extraction_results.py`）— LLM出力はuntrusted

契約v1.1の原則「凍結packet＋raw judgment → deterministic builderが照合」をここでも守る。
**照合は投稿本文に対して行う。** 落ちたものはレポートを作らず `issues` に記録する（fail-closed）。

### ★ 検証と採否は「イベント単位」で行う（v1.2 で明記。v1.1 では粒度を書いていなかった）

1つの投稿に複数イベントが載っているとき、**あるイベントが検査に落ちても、同じ投稿の他のイベントは
そのままレポートにする**。投稿単位で一括に落としてはいけない。

これは仕様が想定している主要ケースそのものだからである——自治体アカウントが複数町会の予定をまとめて
投稿する形（実データでは足立区東綾瀬の1ページに12件）で、**1件でも会場名の書き写しがずれると
その投稿の全イベントが失われる**。しかも state は処理済みになるので二度と読まれず、取りこぼしが恒久化する。

`outcome` はイベント単位の結果をまとめて決める。**1件でもレポートになったら `report`**、
1件もレポートにならず採点だけ残ったなら `scored_only`、検査落ちを含むなら `issue` を併記する
（`report` と `issue` が同時に起きうるので、`outcome` は文字列でなく
`{"report": n, "scored_only": n, "issue": n}` の内訳を持たせてよい）。

| 検査 | 内容 | 落ちたとき |
|---|---|---|
| packet実在 | `no` がそのバッチに存在する | `unknown_packet` |
| 点数の範囲 | `s` が1〜5の整数 | `invalid_score` |
| 引用の実在 | `quote` が本文の部分文字列（正規化後：空白・改行・URLを除去して比較） | `quote_not_in_text` |
| 日付の実在 | `date_start`・`date_end` が `machine_extracted_dates` に含まれる | `date_not_in_text` |
| 日付の向き | `date_end >= date_start` | `date_range_invalid` |
| 日付の未来性 | `date_end`（無ければ `date_start`）が取り込み日以降 | `date_in_past`（§3。issueでなく `scored_only` 扱い） |
| 会場の実在 | `venue_name` が本文（正規化後）に部分文字列として現れる | `venue_not_in_text` |
| 出典 | 投稿URLが空でない | `missing_source_url` |

**`event_name` は照合しない。** 投稿が「◯◯公園で盆踊りやります」としか書いていないとき、
LLMが付ける名前は本文の部分文字列にならない。ここを厳しくすると全部落ちる。
代わりに `quote` を必須にして、名前の根拠を人が後から追えるようにする。
名前が実在イベントとずれていた場合はE2の同一性判定と内田さんの裁定で捕まる。

**教訓の適用（E2 #211/#212）＝「守る」を作るときは禁止の範囲を最小にする。**
捏造されると害が大きいもの（日付・会場・出典）だけを止め、解釈の余地があるもの（名前）は通す。

**点数は全件を `data/x_post_scores.json` へ記録する。** 5点未満でもレポートは作らないが点数は残す
（内田さんの 8/15 の指示＝「捨てるための閾値ではなく、後で並べ替え・見直しをするための記録」）。

## 8. 生成するレポート（`data/x_post_reports/<report_id>.json`）

```json
{"report_type": "official_notice",
 "reported_at": "<取り込み時刻>",
 "source": {"report_id": "x_event_<hash>",
            "title": "<event_name>（X投稿より）",
            "account_key": "<@account>",
            "url": "<代表投稿のURL>",
            "notice_kind": "x_post",
            "raw_text": "<代表投稿の本文全文>"},
 "events": [{"action": "register_new",
             "event_name_hint": "<LLMのevent_name>",
             "event_year": "<date_startから機械が取る>",
             "date_start": "...", "date_end": "...",
             "venue": {"name": "<venue_name>", "area": "<ward>"},
             "detail_addendum": "<§9 のとおり機械が組み立てる>"}]}
```

### 同じイベントの複数投稿を束ねる（流量に直結するので v1 に入れる）

**`report_id` は投稿ごとではなく、提案の中身から決める**＝
`"x_event_" + stable_id(正規化した event_name, date_start, 正規化した venue_name)`。
同じイベントを5人が投稿しても1レポートになり、E0 の `revision_family_key` も1本になる。
日をまたいだ再告知も同じ family に入る。**束ねの判定は正規化文字列の完全一致だけで、意味判定はしない。**

**代表は「そのreport_idで最初にレポートを作った投稿」で永久に固定する**（2026-08-16 おとの指摘で修正。
当初「最も早い `posted_at`」と書いていたが、これはバッチ内でしか成立せず、**日をまたいで
より古い投稿が後から来ると代表が入れ替わってしまう**）。後から代表を変えると `raw_text` が変わり、
`source_payload_hash` が動いて E0 が中身の変わっていない候補に revision を積む（E0b の教訓）。

同じ report_id の2件目以降は、**URLを `detail_addendum` の内部記録行（§9）へ足すだけ**で、
`source.url` / `raw_text` / `events` はいずれも動かさない。既に同じURLがあれば足さない（冪等）。
**後から `date_end` などが判明しても `events` は書き換えない**——書き換えると同じく hash が動く。
取りこぼしはE2の同一性判定と内田さんの裁定で捕まえる。

**1つの投稿に複数イベントが載っている場合は、イベントごとに別の report_id を持つレポートになる**
（report_id が名前・日付・会場から決まるので当然そうなる）。それぞれの `source` は同じ代表投稿を指し、
`raw_text` も同じ本文になる。これは正しい状態である。

`event_year` と `detail_addendum` は**機械が組み立てる**（LLMに書かせない）。`action` は `register_new` 固定で、
既存イベントかどうかはE2が決める。**`venue` に `address` を入れない**——投稿から住所は読めず、
推測で入れると `ensure_venue` の完全一致照合を誤らせて会場を二重に作る（8/7 鹿骨中学校の事故と同型）。

## 9. 出典の扱い（公式と私人で書き分ける）

2026-08-08 の内田さん決定＝**公式・準公式は名前とURLを出す／私人は出さない。ただし情報は使ってよく、
内部の出所記録は残してよい**（公開層の `public_detail_text()` が `- 出典URL:` 形式の行を除去する）。

`assess_source_officiality` の分類で `detail_addendum` を分ける。

- `registered_official_social`（公式・準公式）＝
  `"出典：<account_name>（<@account>）のX投稿。<note>"` ＋ 内部記録行 `"- 出典URL: <url>"`
- それ以外（私人）＝
  `"現地の告知投稿で開催を確認。<note>"` ＋ 内部記録行 `"- 出典URL: <url>"`
  **アカウント名・ハンドルを本文に書かない。**

`<note>` は**回答の `n`（§6 の result レベルにある）**を指す。`events[]` の中ではないので注意。

束ねた2件目以降のURLは、どちらの場合も内部記録行に追記する。

## 10. 流量

パケット側に上限は置かない（全件読ませるため）。下流には既に流量制御があり
（E0 の `--max-candidates` 既定200、E2 の `--max-packets` 既定100）、そこで順に処理される。
取り込みレポートに **5点の件数・生成レポート数・束ねで減った数・未処理の残数**を出し、
**残数が増え続けたら提案を止める**（判断待ち561件の再演を避ける／合意事項2）。

## 11. 不変条件（`docs/spec/` へ追加。同じPRで直すのが大原則）

- **INV-XPE-001**: パケットに載せる投稿を、意味（語彙一致）を理由に除外しない。除けるのは既出・完全重複だけ
- **INV-XPE-002**: LLMの回答は本文と照合され、本文に無い日付・会場を含むイベントからはレポートを作らない
- **INV-XPE-003**: 5点未満の投稿からレポートを作らない。ただし点数は全件記録する
- **INV-XPE-004**: 生成レポートは必ず `source.url` に投稿URLを持つ（出典なしで正本factの材料を作らない）
- **INV-XPE-005**: 生成レポートの `venue` に `address` を含めない（住所は投稿から読めないため）
- **INV-XPE-006**: 私人アカウント由来のレポートは、`detail_addendum` の公開部分にアカウント名・ハンドルを含めない
- **INV-XPE-007**: 回答が返ってこなかった投稿は処理済みにならず、次のパケットで再び出る（読み落としを取りこぼさない）
- **INV-XPE-008**: 束ねたレポートの代表（`source.url` / `raw_text` / `events`）は、後から来た投稿で書き換わらない
- **INV-XPE-009**: 累積の `voices.json` から、既定で前日以降の投稿だけをパケット化する。
  1回あたりのバッチ数にも上限を置き、**超えた分は捨てずに次回へ残す**

## 12. 受け入れ条件（negative test。各件「修正を外したら落ちる」ことを確認する）

**パケット生成とstate（§5）**

1. `applied_at` を持つ投稿は再度パケットに出ない
2. `issued_at` があり未処理で24時間以内の投稿はパケットに出ない（回答待ちの二重出力を防ぐ）
3. `issued_at` から24時間を過ぎた未処理の投稿は、再度パケットに出る（**回答が来なかった分を取りこぼさない**）
4. `--reissue` を付けると、2の抑止が無効になり未処理分が再度出る
5. 本文が正規化後に同一の投稿は1件だけパケットに出る
6. 盆踊り語を含まない投稿もパケットに出る（INV-XPE-001。**意味で除外していないことの確認**）
7. 月日だけの日付は `posted_at` の年で補われ、投稿月より2か月以上前になる場合は翌年になる
8. 時刻表現（「18時」）は `machine_extracted_dates` に入らない

**取り込みと検証（§7）**

9. `quote` が本文に無い回答はレポートを作らず `quote_not_in_text` を記録する
10. `date_start` が本文に無い回答はレポートを作らず `date_not_in_text` を記録する
11. `date_end < date_start` の回答は `date_range_invalid` を記録する
12. `venue_name` が本文に無い回答は `venue_not_in_text` を記録する
13. `no` が不明な回答は `unknown_packet` を記録する
14. 4点以下の回答からレポートは作られない。ただし点数は `x_post_scores.json` に残る
15. **5点でも `date_end`（無ければ `date_start`）が過去ならレポートを作らず、`scored_only` として処理済みになる**
16. apply後、そのバッチの全packetが `applied_at` を持つ（`issue` も `scored_only` も含む）

**束ね（§8）**

17. 同じ「名前・日付・会場」を指す3件の投稿から、レポートは1本だけできる
18. **後から `posted_at` がより早い投稿が来ても、代表（`source.url` / `raw_text`）は入れ替わらない**
19. 後続投稿の情報で `events`（`date_end` 等）が書き換わらない
20. 束ねた2件目以降のURLが `detail_addendum` の内部記録行に入る
21. 既に内部記録行にあるURLは二度足されない
22. 1つの投稿に2イベントが載っている回答から、別々の report_id を持つレポートが2本でき、
    どちらも同じ代表 `source.url` を指す
22b. **1つの投稿の2イベントのうち片方が過去日でも、未来日のもう片方はレポートになる**
22c. **1つの投稿の2イベントのうち片方が検査落ち（会場が本文に無い等）でも、正しいもう片方はレポートになる**

**出力（§8・§9）**

23. 私人アカウント由来のレポートの `detail_addendum` にハンドル名・アカウント名が現れない
24. 公式アカウント由来のレポートの `detail_addendum` にはアカウント名が現れる
25. 生成レポートに `venue.address` が含まれない
26. `event_year` は `date_start` から機械が決める（LLMが別の年を書いても無視される）
27. 同じ回答を2回取り込んでもレポートは1本（冪等）
28. 生成レポートが E0（`build_event_inbox_candidates.py --report-dir data/x_post_reports`）で
    `event_create` レーンの候補になる（結合テスト）
