更新: 2026-06-25T23:54:15+09:00 / 署名: おと（Codex）。1番の深掘り結果。

### 結論

* build_all_rdb.py は手動で実行タイミングを覚える対象ではない。ただし現状のまま全workflowへ差し込むのも不適切。
* 方針はハイブリッド。読み取り・再生成・監査・レビュー材料作成は自動化し、Notion本番同期や公開デプロイの判断には使わない。
* まず rdb-light / rdb-full / rdb-report-only の3モードに分ける。

### 検証結果

* ローカルで /tmp 出力により、Notion APIなしの軽量再生成を検証済み。既存 data/notion_snapshot.sqlite を入力に、evidence/youtube/bon_odori/review report まで生成できた。
* light検証の主な件数: evidence source_posts=8527、youtube videos=4307、bon_odori events=222、venues=213、evidence_items=10558、review_queue=29510。
* Git作業ツリーは検証後も clean。SQLite本体は data/*.sqlite として gitignore 対象。

### 制約

* GitHub Actions には data/notion_snapshot.sqlite が存在しない。SQLiteはgitignore対象なので、lightをそのままActionsへ入れると横断RDB生成で止まる。
* fullは build_notion_rdb.py を含むため NOTION_API_TOKEN が必要。Notionは現在の公開正本ではないので、毎回正本扱いで使ってはいけない。
* rdb_review_queue / rdb_event_apply_plan / rdb_song_review_source は合計約2.5MBあり、自動コミット対象にすると差分が大きくなりやすい。
* export_rdb_apply_plans.py は出力先オプションが弱く、tmp検証やActions artifact運用には少し直した方がよい。

### 推奨設計

* rdb-light: Notion再取得なし。既存snapshotがある環境で evidence.sqlite、youtube_evidence.sqlite、bon_odori.sqlite、review summary を再生成する。ローカル日次後処理の本命。
* rdb-full: build_notion_rdb.py から実行。Notion snapshot更新が必要なときだけ。週次または手動ボタン向き。
* rdb-report-only: 既存SQLiteからレビューJSON/MDとサマリーだけ再生成。作業後の確認やPRコメント用。
* Actionsでは、まず summary/report を artifact または小さいJSONとして残し、巨大なレビューJSON/MDを毎回mainへ自動コミットしない。

### 組み込み候補

* YouTube daily後: 候補・setlist・active reviewが動くため、rdb-light相当を走らせたい。ただしActionsではNotion snapshotがないので、最初はsummary artifactかPR branch限定。
* collect日次後: voices、x_account_scores、public exportが動く。RDBはレビュー材料として有用だが、公開デプロイの条件にはしない。
* weekly harvest後: 曲候補・用語候補と関連するため、report-onlyまたはlightでレビュー元データを更新する価値が高い。
