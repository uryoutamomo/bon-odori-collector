## 0. 背景と、内田さんの判断（2026-08-13）

2026-08-11 の再評価で、X収集で毎日読む250人が「有用度スコア（`usefulness_score`）の上位250」で選ばれており、その点数が満点100に張り付いているため、実際にはハンドル名のアルファベット順で切れていることが分かった。2026-08-13 に本日時点の台帳（`data/x_account_scores.json`・2026-08-12T08:02Z 生成）で測り直したところ、状況は変わっていなかった。

- 選抜条件を満たす候補 1,027人のうち **261人が満点100**
- 選ばれた250人の点数レンジは **100〜100**（点数では誰も区別できていない）
- 切れ目は `@yamashita99`（250位・採用）と `@yan_su_su`（251位・落選）の間
- 選ばれた250人のうち **71人は23区の盆踊り投稿がゼロ**、**21人は `is_area_bot`**、**27人は告知力・記録力とも3点未満**

これを受けた内田さんの判断は次の3つ。

1. **2軸（告知力 `announce_score` / 記録力 `record_score`）への切り替えはOK。**
2. **まったく別に、公式・準公式のアカウントは台帳へ記録しておく。** これからのイベント、あるいは来年のイベントの告知がないかを確認するときに活用する。終わったイベントの公式アカウントや準公式（主催者などの関係者、政治家）は「来年に取っておく」。
3. **2つ以上のイベントを発信している公式は、単に記録するだけでなく活用する。**

つまり、「毎日読む名簿」と「情報源として保管する台帳」を別のものとして扱い、台帳の中から条件を満たすものだけを毎日読む側へ引き上げる、という構造にする。

## 1. 用語

| 語 | 意味 |
|---|---|
| 盆踊ラー名簿 | 2軸スコアで選ぶ、個人中心の直読み対象。従来の `auto_trusted_roster` の後継 |
| 公式ソース台帳 | 主催者・町会・神社・自治体など、行事の一次情報を出す組織アカウントの記録 |
| 準公式 | 主催者側の関係者・議員・地元企業・施設など、当該行事について一次情報を出すが主催者本人ではないもの |
| active | 毎日の直読み対象に入っている状態 |
| dormant | 台帳には残すが読まない状態。条件を満たすと自動で active へ戻る |
| 紐付け（linked event） | そのアカウントが発信している行事（`event_series`）との対応 |

## 2. 選抜A：盆踊ラー名簿を2軸へ切り替える

### 2.1 現行から変えること

`collect.py` の `_auto_trusted_roster_accounts()` が使う並び替えキーを `usefulness_score` から2軸へ変える。**`usefulness_score` の計算自体は消さない**（`evidence` RDB へ永続化されており、レビューコンソールの表示にも使われている）。変えるのは「誰を読むかを決めるときに何を見るか」だけにする。

### 2.2 新しい選び方

告知の名簿と記録の名簿を**別々に作り、和集合を取る**。内田さんの指示どおり、両方に載る人がいる前提にする。

```
告知名簿 = announce_score 降順の上位 150人
記録名簿 = record_score  降順の上位 150人
直読み対象 = (告知名簿 ∪ 記録名簿 ∪ 手動優先 ∪ 公式台帳のactive) − 人手除外台帳
```

- **人数を150+150にした理由**: 現行の250人・$0.1176/日 という費用感を大きく変えないため。本日のデータ（母集団＝投稿3件以上・bot除外・人手除外/休止を除く 1,001人）で和集合を取ると **234人**（うち両方に入る重複 66人）、手動優先を足して **239人**となり、現行250人とほぼ同じ規模に収まる。重複が出ることは「両方できる人がいる」という内田さんの前提そのものなので、重複ぶんを埋め戻して250にはしない。
- **切り替えで起きる入れ替わり**: 現行250人との重なりは131人で、**新しく読むのが103人、読むのをやめるのが119人**。半分近く入れ替わる変更なので、切り替えた最初の1週間は、それまで拾えていた投稿が拾えなくなっていないかを `data/x_review_lanes.json` の件数で見る。
- **手動優先は明示的に足す必要がある**: 手動優先11人のうち **5人は2軸の上位300に入らない**。和集合だけで名簿を作ると人の判断が消える。
- **同点時の並び**: 現行はハンドル名のアルファベット順で、これが今回の不具合の温床になった。第2キーを `bon23_count`（23区の盆踊り投稿数）降順、第3キーを `distinct_post_days` 降順とし、**アルファベット順は最後の最後だけ**にする。
- **足切り**: `posts_with_text >= 3` を維持する。比率が1件で満点になる問題は式側の縮約で対処済みだが、量の裏付けがない人を上位に入れない。

### 2.3 機械が触ってはいけないもの

- `data/x_collection_roster.json` の `manual_status: 優先` は**無条件で直読み対象に含める**。過去に試作v2で `@niinobon_uta` が落ちた。人の判断を機械が毎日巻き戻さない。
- `data/x_roster_exclusions.json` にあるものは**無条件で外す**。
- `manual_status: 休止` は外す。
- `is_area_bot` は外す。ただし bot 判定で外せるものを人手の除外台帳へ書き足さない（ロジックの検査ができなくなるため）。

### 2.4 23区外の扱い

**人は残す。外すのは地域ニュースbotだけ。** 23区外で活動する盆踊ラーの投稿は、曲や踊りの話として盆助のコンテンツに使える。`outside_ratio` を選抜条件にしてはいけない。

## 3. 台帳B：公式・準公式ソース台帳

### 3.1 どこに書くか

**新しいファイルを作らず、既存の `data/x_official_source_accounts.json` を拡張する。** このファイルは既に `related_event_keywords` という紐付け用のフィールドを持っており、`collection_support/x_official_source_accounts.py` と `collection_support/x_source_officiality.py` から読まれている。現在の登録は `@iri2choukai`（入船二丁目町会）の**1件だけ**で、実質的に空の器になっている。

### 3.2 対象の定義

| 種別 | 具体例 | 台帳での扱い |
|---|---|---|
| official | 町会・自治会・商店会・振興組合・実行委員会・保存会・神社仏閣・観光協会・区役所/自治体・行事の公式アカウント | 記録する |
| quasi_official | 主催者側の関係者、区議・都議・国会議員、会場となる施設、地元企業・店舗 | 記録する。ただし既定は dormant（3.5参照） |
| （対象外） | 行事と紐付かない企業公式、全国イベントまとめbot、他地域ニュースbot | 台帳へ入れない |

### 3.3 検出のしかたと、その落とし穴

検出は3つの材料を使う。優先度の順に並べる。

1. **アカウント表示名（`voices[].name`）** — いま唯一まともに使える材料。本日の実測（ローカル `data/voices.json`・X由来8,902件・2025-11-08〜2026-07-27）で、表示名に組織語を含むアカウントが **272件**、議員などの語を含むものが **258件** 見つかった。
2. **プロフィール文（`voices[].profile_description`）** — **⚠️ 現在まったく使えない。** PR #176 で保存を実装したが、2026-08-12 生成の `data/x_account_scores.json` 全13,604件のうち、プロフィール文が入っているものは **0件** だった。既存の `collection_support/x_source_officiality.py` の組織語判定はプロフィール文に依存しているので、**この状態では公式判定がほぼ機能しない**。原因の調査は 6.1 に宿題として書く。
3. **投稿本文の型** — 日時・会場・主催表記が揃った告知文。既存の `SCHEDULE_HINT_RE` / `BON_HINT_RE` を使う。

**落とし穴：「公式」という語だけで拾ってはいけない。** 実測すると「シモジマ【公式】」「仮面女子:公式ツイッター」「高島易断神聖館【公式】」のような、盆踊りと関係のない企業・団体が同じ網にかかる。**盆踊り行事への紐付けが1件以上あることを、台帳へ入れる必須条件にする。**

### 3.4 行事との紐付け方（ここが実装の核心）

**イベント名の完全一致で引いてはいけない。** 本日の実測では、公式らしい530アカウントのうちイベント名で紐付いたのは **29件だけ**で、501件は0件だった。これは既知の弱点（YouTube証拠99件中、イベント名の完全一致で引けたのは6件）と同じもので、`event_series.canonical_name` と人が書く名前は一致しない。

代わりに **会場と地名で当てる**。実測でも、イベント名では0件だったアカウントが会場名では複数当たっている（例: `@nakayamashizu`＝板橋区選出の都議、イベント名0件・会場名5件）。

紐付けの判定は次の積で行う。

```
紐付け成立 = 会場名または地名の一致
           かつ 区市町村が矛盾しない
           かつ 盆踊り語を含む
```

- 会場名は `venues.canonical_name` に加えて **`data/venue_surface_form_observations.json`（表記ゆれを確率つきで持つ正本）** を使う。会場名が壊れている裏取りキューの値で突き合わせない。
- 地名は `event_model/place_dictionary.py` の `place_nodes` / `place_aliases` を使う。**⚠️ PR #181 の migration は本番RDBへ未適用**なので、未適用のあいだは `venues` だけで動くこと（fail-safe）。
- **区市町村の矛盾チェックは必須。** 「浜町公園」は川崎市にも日本橋浜町にもあり、「中島公園」は札幌にもある。`collection_support/tokyo23_scope.py` の既存資産（`NON_TOKYO_PREF_RE` / `TOKYO_23_WARDS`）を使い、政令市の同名区を先に打ち消す。
- 一般名詞の会場・行事名（「盆踊り大会」「〇〇公園」単体）では紐付けない。5文字未満の会場名は照合対象から外す。

紐付けには確からしさを持たせる。

| confidence | 条件 |
|---|---|
| confirmed | 人が確認した、または会場一致＋区一致＋日付一致が同一投稿内で揃っている |
| probable | 会場一致＋区一致（日付なし）が2投稿以上 |
| possible | 上記が1投稿だけ。台帳には入れるが active へは引き上げない |

### 3.5 台帳のスキーマ

既存の行を壊さず、フィールドを足す形にする。

```json
{
  "handle": "@iri2choukai",
  "name": "入船二丁目町会",
  "source_type": "official",
  "trust_level": "organizer_official",
  "tier": "dormant",
  "linked_events": [
    {
      "series_id": "ser_xxxx",
      "series_name": "鉄砲洲納涼盆踊り",
      "ward": "中央区",
      "confidence": "confirmed",
      "first_seen": "2026-07-14",
      "last_seen": "2026-08-02",
      "evidence_urls": ["https://x.com/iri2choukai/status/…"],
      "latest_occurrence_end": "2026-08-02",
      "expected_month": 8
    }
  ],
  "wake_after": "2027-06-03",
  "sleep_after": "2026-08-16",
  "decided_by": "machine",
  "decided_at": "2026-08-13",
  "notes": "…"
}
```

`related_event_keywords`（既存）は残す。人が手で書いた手掛かりなので、機械が消さない。

### 3.6 active / dormant のライフサイクル

毎日、台帳の各行について次の順で判定する。**上に書いたルールが優先。**

1. `decided_by: user` で `tier` が明示されている → **その値を機械が変更しない**。**`decided_by` を持たない既存行も人が手で書いたものとして扱い、機械は降格させない**（この台帳は元々人が手で作ったので、印が無いことは「機械のもの」を意味しない）
2. **異なる行事 2件以上**に紐付く → **active**（内田さんの指示。行事をまたいで発信する公式は常に読む価値がある）。**ここでは confidence を問わない。** 別々の行事でそれぞれ会場が一致することは偶然では起こりにくく、複数行事を発信していること自体が裏付けになるため。実測でも、板橋区選出の都議が5つの町会盆踊りを、大田区商店街連合会が2つの町会盆踊りを告知しており、これらを possible だからと除くと内田さんの指示が空振りする
3. `linked_events` が1件で、その行事の今年の開催回が**まだ終わっていない**（`date_end` または `date_start` が今日以降）→ **active**
4. `linked_events` が1件で、終了から **14日以内** → **active**（御礼投稿・当日の記録・来年の予告が終了直後に出るため）
5. `linked_events` が1件で、来年の開催予測日まで **60日以内** → **active**（起こす）
6. 上のどれにも当たらない → **dormant**（読まない。台帳には残す）
7. `linked_events` が1件だけで possible → **pending_review**（人が見るまで読まない）
8. `linked_events` が0件でも、**表示名に組織・議員の語があり、かつ盆踊り語を含む投稿が1件以上ある** → **unlinked**（読まないが台帳には残す）。内田さんの指示は「公式や準公式のアカウントは記録しておくべき」なので、紐付けが取れないことを理由に記録ごと捨てない。人が後から会場や行事を補って active へ引き上げられる置き場として使う

**⚠️ ここでの「読まない」は「台帳が読ませない」ではない（2026-08-13 実測で判明・修正済み）。** active 以外の行を `load_whitelist_accounts()` へ「休止」として供給すると、この一覧は2軸名簿より**先に**組まれてハンドルで重複排除されるため、**2軸名簿が選んだ人が台帳の都合で黙らされる**。ローカル実測（voices 10,630件・台帳321件・2軸名簿233人）で **25人**がこれで消えており、内訳は unlinked 23人・pending_review 2人、その中に神田観光協会（`@kandakankou`）のような、検索でしか拾えていない一次情報源が含まれていた。読む件数は 238 → **265** になる（費用の増分は 27人×$0.00044＝約 **$0.012/日**）。したがって **active 以外の行は台帳から直読み名簿へ供給しない**。台帳は「その相手が何であるか」の記録であって、読むか読まないかを決める権限は持たせない。

**⚠️ 表示名の語だけで組織と判定してはいけない。** 実測で、歌手のアカウントが表示名にライブ予定「6/14(日)大井蔵王権現神社前」と書いていたために「神社」で組織と誤判定された。`神社` `稲荷` `八幡` `氷川` `寺` `睦` は会場名や地名として個人の表示名にも現れる。**表示名に日付付きの予定が並んでいる場合はこれらの語を無効にする**、または組織語が表示名の主要部（末尾または区切りで独立している）である場合に限る。`議員` `区議` `都議` は誤検出がほぼ無く（実測234アカウント）、そのまま使える。

**60日という数字の根拠**: 本日の実測で、盆踊りの告知投稿が開催の何日前に出るかを2,289件分の日付言及から測ったところ、中央値は14日前、30日前までに72.5%、**45日前までに85.4%、60日前までに92.3%**、90日前までに98.8%だった。60日前から起こせば告知の9割以上を取り逃さず、かつ1年のうち読む期間は2か月で済む。

**準公式（議員など）の既定は dormant にする。** 理由は、2026-08-11 に評論軸を廃止したときの実測で、盆踊りに触れる政治家の投稿の大半が地域あいさつであり（1人で22件書く例もあった）、毎日読むとノイズと費用に見合わないため。ただし紐付いた行事の時期には上のルール4・5で自動的に起きるので、「来年に取っておく」という内田さんの要求は満たす。

**来年の開催予測日の求め方**: `event_occurrences` の同一 `series_id` の過去実績から、`project_bon-odori-unified-prediction-model` の既存の予測（`predicted_occurrence_dates`）があればそれを使う。無ければ**前年の開催日の同月同週の曜日**を仮の予測日として使い、`confidence: low` を付ける。予測が無いことを理由に起こし忘れない。

### 3.7 読む頻度

active の公式アカウントは、盆踊ラー名簿と同じ日次の直読みに入れる。ただし **1アカウントあたりの取得ページ数は1ページに固定**する（公式アカウントは投稿数が少なく、深追いしても費用が増えるだけ）。

## 4. 日次への組み込みと費用

現行の直読みは268アカウントで **$0.1176/日**（2026-08-11 実測・`docs/x-collection-cost-log.md`）。

- 盆踊ラー名簿の実効は232人まで下がる（現行250人）
- 公式台帳の active は、8月の最盛期でおおむね30〜60件、冬期は10件未満と見込む（紐付けが成立した公式のうち、開催60日前〜終了14日後に入るものだけが起きるため）

したがって日次の直読みは 8月で 262〜292アカウント、冬期は 240前後となり、**現行と同程度**に収まる。名簿の入れ替えは費用削減の施策ではなく精度の施策であることを、ここで改めて明記しておく（削減の本命は証拠掘りコホートの $0.3303/日）。

## 5. 検査（この一覧が受け入れ条件）

実装は次のテストを持つこと。**修正を外したら落ちることを確認する**（テストが通ることは合格の根拠にならない）。

### 選抜A

1. `usefulness_score` が全員100の入力でも、`announce_score` / `record_score` の差で順位が決まること
2. 手動優先（`@niinobon_uta` 相当）が2軸の点数に関わらず直読み対象に残ること
3. 人手除外台帳（`@prtimes_etm` 相当）が2軸の点数が高くても入らないこと
4. `is_area_bot` が入らないこと。かつ `@kobejournal`（神戸）`@goguynet_osaka`（大阪）が、23区判定が1件増えても名簿へ戻らないこと
5. 23区外で活動する個人（`outside_ratio` が高い人）が、それだけを理由に落ちないこと
6. 同点時にハンドル名のアルファベット順が第1キーにならないこと

### 台帳B

7. 表示名に「【公式】」を含むが盆踊り行事へ紐付かないアカウント（`シモジマ【公式】` 相当）が台帳へ入らないこと
8. 「浜町公園」を含む川崎市の投稿が、日本橋浜町の行事へ紐付かないこと
9. 「中島公園」を含む札幌の投稿が、23区の行事へ紐付かないこと
10. 一般名詞だけの投稿（「盆踊り大会に行ってきた」）で紐付けが成立しないこと
11. `decided_by: user` の `tier` を機械が上書きしないこと
12. 終了した行事1件だけを持つ公式が、終了14日後に dormant へ落ちること
13. 同じ公式が、翌年の予測開催日の60日前に active へ戻ること
14. 予測開催日が無い場合でも、前年実績から仮の予測日が立ち、起こし忘れないこと

### 6.3 判断済みの再提示を防ぐ台帳（2026-08-13 決定・実装済み）

pending_review へ入れた公式アカウントを人が「対象外」と判断したとき、その判断を残す場所が無かった。放っておくと毎日同じアカウントが提示される（ゐの市で起きたのと同じ構図）。**台帳内に `tier: "rejected"` を持たせる方式を採った。**

`data/x_roster_exclusions.json` を流用しなかったのは、**2つが別の問いに答えているから**である。あちらは「毎日読む盆踊ラー名簿から外す」判断で、こちらは「公式ソースとして扱わない」判断である。**公式ソースとしては使えないが盆踊ラーとしては読む価値がある、というアカウントは普通にある**（実測で、盆踊りに触れる政治家の投稿の大半は地域あいさつだったが、その人が踊りの話を書かないという意味ではない）。1つのファイルに混ぜると、公式判定の都合で人を名簿から静かに落とすことになる。加えて `x_roster_exclusions.json` は「機械では判定できなかったもの」の一覧＝ロジックの検査材料でもあり、目的の違うものを混ぜると検査として読めなくなる。

書き方と読み方は次のとおり。

- 判断は `python3 review_x_official_sources.py` から行う。`list` で確認待ちを見て、`reject <handle> --reason "…"`（理由は必須）、`accept`、`reopen`（判断の取り消し）。X API は呼ばず、触るのは台帳ファイルだけ
- `reject` は `tier: rejected` / `decided_by: user` / `decided_at` / `decision_reason` を書く
- **`tier: rejected` は `decided_by` が無くても機械が変更しない。** 印を必須にしたせいで手登録の `@iri2choukai` が降格した前例があるため、rejected だけは印より先に見る
- **rejected の行は `load_official_source_accounts()` が返さない。** 「休止」として返すと、この一覧は盆踊ラー名簿より先に組まれてハンドルで重複排除されるため、公式として外しただけのアカウントを直読み全体から消してしまう
- pending_review の行には `pending_since`（最初に人が要ると判定された日）を持たせ、日次ログへ `[official-registry] 要確認 N件（本日新規 A件 / 継続 B件） / 人が対象外と決めたので再提示しなかった C件` を出す。**誰も見ていないキューが「新しい」ように見えないようにするため**

検査は `tests/test_x_official_source_rejection.py`。保護を1つずつ外すと落ちることを確認済み。

**残っている近い問題（今回は直していない）**: `dormant` の行も `load_official_source_accounts()` が「休止」で返すため、同じハンドルが盆踊ラー名簿の上位にいても直読みから外れる。季節外の町会などで起こりうる。読む件数と費用が変わる変更なので、切り離して判断する。
