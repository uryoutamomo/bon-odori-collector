# 地名辞書 v1 仕様（2026-08-12）

内田さんの指示から。

> 界隈の略称、イベント会場、を地名として認識して欲しい。そのためには地名辞書が太るのは
> やむを得ないと思います。また表記揺れも発見次第、判定して組み込んで欲しい。そんな地名に
> 特化した辞書を充実させるのも将来のために役立つと思っています。なので、地名のデータは
> 東京など都道府県、２３区の区、町名などの地名、公園や神社寺など会場名、さらにいえば
> 敷地のどこが盆踊り会場なのか（日枝神社の時みたいに）の情報などを

## 1. なぜ作るのか

X投稿の23区判定を、コードに手で書いた地名リストで行っていた。実データで確かめると、
**「神楽坂の盆踊りへ」「木場一・六町会盆踊り大会」「曙橋通り商店街盆踊り」「DAIBON、大盆踊り会」が
判定できなかった**。神楽坂も木場も、手で書けば入れられる地名である。つまりこれは
足し忘れではなく**手で書く方式そのものが持つ穴**で、足し続けても塞がらない。

ことは当初「辞書が太ると都外のアカウントが誤って23区と判定される」と警戒したが、
それは**辞書が平たいまま太る**場合の話だった。階層を持たせれば、太るほど判定は正確になる。
「木場」を平たいリストに足せば他所の木場と衝突するが、「木場＝江東区の町名」として
親子で持てば衝突しない。

## 2. 構造（おとと合意した設計）

master RDB に **`place_nodes` と `place_aliases` を独立して置く**。

| 階層（`place_type`） | 例 | 内田さんの言葉 |
|---|---|---|
| `prefecture` | 東京都、千葉県 | 東京など都道府県 |
| `municipality` | 中央区、市川市 | 23区の区 |
| `locality` | 神楽坂、木場、月島、佃、曙橋 | 町名などの地名 |
| `site` | 日枝神社、木場公園、築地本願寺 | 公園や神社寺など会場名 |

**⚠️ 敷地内のどこが会場かは、階層に入れない**（2026-08-12 内田さんの判断）。

> 敷地内の場所なくても良くてイベント本文で補うのが良いかも

初版では `subsite` として第5階層に持つ案だったが、**イベントの本文（説明文）で補う**形にする。
理由として妥当なのは、櫓の位置が年ごとに変わりうること（「今年は正門側」）、
構造化しても検索や判定に使う場面が無いこと、そして文章なら「参道を入って右手の広場」のように
**人が読んで分かる粒度で書ける**こと。管理の手間に対して得るものが少ない。

```
place_nodes(place_id, place_type, canonical_name, normalized_name,
            parent_place_id, latitude, longitude, memo,
            source, confidence, review_status, created_at, updated_at)
place_aliases(place_id, alias, normalized_alias, source, confidence)
```

### 2-1. 23区かどうかは列に持たない（重要）

`is_tokyo23` を各行に持たせない。**`parent_place_id` を根までたどって導出する。**
「山王祭の櫓の位置 → 日枝神社 → 永田町 → 千代田区 → 東京都」とたどれば、
末端に区名を書き忘れても正しく決まる。**書き忘れによる穴が構造的に生まれない**のが要点で、
これは今回の再評価で何度も踏んだ失敗（手書きリストの穴が人の減点になる）への答えである。

runtime の高速化キャッシュとして `is_tokyo23` を持つのは構わないが、
**RDB の正本値にはせず、親鎖からいつでも再生成できる状態を保つ。**

### 2-2. 既存 `venues` は業務エンティティのまま残す

`venues`（402件）は「開催回が使う会場」という業務上の実体で、これは地名ではない。
親子を直に足すと、地名・敷地内の場所・業務上の会場の意味が混ざり、既存402件の移行も難しくなる。

**`venues.place_id`（optional）で `site` ノードへリンクする**形にする。
リンクが無い会場があってよい（未整備のまま運用を止めない）。

### 2-3. 用語集v2 は「人が育てる入口」に徹する

用語集v2 は表記ゆれと界隈語を人がレビューして登録する場所。
**`term → place_id`（または venue_id / series_id）を解決済みの型付き alias として出す。**
X判定器はそのIDから親をたどる。曖昧・未解決は今までどおり unknown で中立に置く
（[[x-bonodorer-reevaluation-20260811]] 第3版13節の原則を壊さない）。

PR #180 で入った `entity_aliases`（term/canonical/entity_type）が、この入口の第一段である。

## 3. 初期データの入れ方

1. **`prefecture` 47件**と**`municipality`（23区＋主要市）**を先に置く。ここは公的な区分なので機械的に入る
2. **`site`** は既存 `venues` 402件から起こす。`area` は「江戸川区57／江東区37／世田谷区33／
   品川区26／墨田区25…」と区名が入っているので `municipality` へ紐付けられる。
   **ただし `address` が空の会場が29件ある**ので、それらは親不明のまま置き、後で埋める
3. **`locality`** は当面、判定に必要なものから入れる。今回見つかった神楽坂・木場・曙橋に加え、
   `venues.address` から町名を抽出して候補にできる
4. 敷地内のどこが会場かは、上記のとおり**イベントの本文で補う**。
   この情報は実際に足を運んだ人の記録からしか得られないので、供給源は
   X の参加記録（記録軸で拾っている投稿）と掲示物レポート経路になる

## 4. 表記ゆれを育てる流れ

内田さんの「表記揺れも発見次第、判定して組み込んで欲しい」への対応。

- X投稿に出てくる**未解決の語**（どのノードにも解決しなかったもの）のうち、
  盆踊りの文脈にあり頻度が高いものを候補として溜める
- 人（内田さん or こと）が「これは町名」「これは会場の通称」と**型を付けて**承認する
- 承認されたものだけが `place_aliases` に入る。**機械が勝手に足さない**

盆オドラーの棚卸しと同じ考え方で、機械は候補を並べるところまで、決めるのは人。

## 5. 段階

| 段 | 内容 | 完了条件 |
|---|---|---|
| P1 | `place_nodes` / `place_aliases` のスキーマ新設と、prefecture・municipality の投入 | 親鎖から23区かどうかを導出する関数が動くこと。既存の収集・公開に影響がないこと |
| P2 | `venues` 402件から `site` を起こし、`venues.place_id` でリンク | address が空の29件は親不明で置く。**既存の会場データを書き換えない** |
| P3 | 用語集v2 → `place_id` 解決の配線。神楽坂・木場・曙橋・DAIBON を投入して効果を測る | 4例が23区と判定できること。**教師データの負例が救済されていないこと**（辞書が太ると都外が誤判定される危険。とくに `@kobejournal`・`@goguynet_osaka` は bot 条件が `bon23_count == 0` なので、1件でも増えると名簿へ戻る） |
| P4 | 未解決語の候補収集と承認の流れ | 機械が勝手に辞書へ足さないこと |

## 6. 判定以外の価値

敷地内のどこに櫓が立つかは、判定の精度より**公開サイトの価値**として大きい。日枝神社のように
広い境内だと、参拝の入口と櫓の位置は違い、初めて行く人は迷う。構造化データではなくイベント
本文で持つと決めたが、価値が下がるわけではない。この情報は実際に足を運んだ人の記録からしか
得られないので、**X の参加記録軸で拾おうとしているものが、そのまま公開情報の質につながる**
という関係は変わらない。
