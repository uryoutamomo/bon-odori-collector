## 2. 診断

**すべてのX経路の真ん中に「エージェントが全件を手で解釈する」工程があり、渡される量が
人間（エージェント）サイズを大幅に超えているため、必ず止まる。**

- 経路A: 7,235件 → おとが解釈 → 7/12で停止（49件処理）
- 経路B: 2,214件 → ことが読む → 3件で停止
- 経路C: 2,460件 → 担当が定義されていない → 0件

そして2026-07-26の改修（PR #114）は、検索3→8ページ・クエリ7→11本・名簿69→264件と
**入口だけを広げた**。ボトルネックは入口ではなく処理側の帯域だったため、未処理の山を
厚くする結果になった（ポスターキュー1,789→2,214件）。ここは見立てを誤っていた。

配管（review_inbox → staged decision → change_requests → apply_change_requests → RDB
→ 公開JSON → S3）は**コードとしては存在する**。`review_inbox_adapters/build_change_requests_from_review_inbox.py`
が既存 occurrence への `confirm_current_date` / `promote_historical_reference` /
`fill_venue` を change_request へ翻訳する。

**ただし一度も通し実行されていない**（2026-07-28 追記・要注意）:

- `data/review_console/staged/` は**存在しない**。`apply_review_console_decisions.py --write`
  が作るはずのステージ出力が、一度も生成されたことがない。
- したがって `build_change_requests_from_review_inbox.py` の入力
  （`data/review_console/staged/review_inbox_change_request_decisions.json`）も存在しない。
- **「配管が完成している」と考えてはいけない。「部品は揃っているが通電したことがない」**が
  正確な状態。P2/P3では end-to-end の疎通確認を独立した受け入れ条件として扱う。

さらに別セッションの監査（2026-07-27夜、`review_console/data.py` の日本語化を実施した回）で、
**`domain_stage` 行きの118件（YouTube証拠99件＋用語/曲/会場候補19件）には、下書きを読んで
RDBへ反映するコードがリポジトリに存在しない**ことが判明している。定義・テスト・docsにしか
出てこない。押しても何も起きないボタンになっている。

つまり **足りないのは「量の制御」と「Xから受信箱への入口アダプタ」と「受信箱から先の通電確認」の3つ。**

## 3. 設計原則

> **経路の真ん中にいるエージェントに、1日あたり処理し切れる量しか渡さない。
> 渡す量は機械が事前に決め、あふれた分はキューに積まずアーカイブへ流す。**

数値目標（設計上の定数として扱う）:

| 誰が | 1日あたりの上限 | 現状 |
| --- | --- | --- |
| こと／おとが解釈する件数 | **30件** | 7,235件（実処理0） |
| 内田さんが判断する件数 | **3件** | 0件（受け皿に406件滞留） |

3件に絞り切れないなら、それは前段の絞り込みが甘い証拠なので、**上限を上げるのではなく
絞り込み側を直す**。これを運用ルールとして固定する。

## 4. 再設計

### 4.1 拾う — 穴埋め駆動（gap-driven）に反転する

いまは「盆踊り」で広く拾ってから薄いスコアで仕分けている。これを逆にして、
**master RDB が今持っている穴を起点に、その穴を埋める投稿だけを引き当てる**。

日次で以下の「穴」を RDB から列挙し、それぞれに対して voices から証拠を引く:

1. **開催日が未確定のイベント**（2026年で68件）— `date_start` が空の occurrence
2. **既存イベントの状態を壊す情報** — 中止・順延・延期・時刻変更。取りこぼすと
   公開サイトが嘘をつくので、他より優先度を上げる
3. **公式アカウント発の新規イベント** — `data/x_official_source_accounts.json` 由来で、
   既存 series にも alias にも一致しないもの
4. 上記で30件に満たない場合のみ、確度スコア順で埋める

イベント名・会場名の突合には `event_series_aliases`（2026-07-27にPR #118/#119で整備済み）
と `venue_aliases` をそのまま使う。

この絞り方が有効なことは実証済み。`build_event_poster_ocr_queue.py` が
「開催日未確定イベントに触れている投稿を先頭に並べる」方式で2,214件→39件まで落として
おり、2026-07-26に実際に3件を反映できた唯一の経路がこれ。同じ考え方を全カテゴリへ広げる。

**あふれた約7,200件の扱い**: 捨てない。`evidence.sqlite` に保持したまま、キューには
出さない。後から「このイベントの根拠を探したい」時に検索して引ける状態を維持する。
**「全部処理しなければ」という前提を明示的に捨てる**のが、この設計の要点。

広く拾う `q-base` 系クエリは「まだ知らないイベントの発見」用に残すが、出口はレーン3
（下記4.3）へ分ける。

### 4.2 反映 — 既存の配管に繋ぐ。新規実装は入口アダプタだけ

| 情報の種類 | 使う経路 | 状態 |
| --- | --- | --- |
| 既存イベントの日付確定・会場補完・過去実績昇格 | review_inbox → staged → `build_change_requests_from_review_inbox.py` → `apply_change_requests` | **部品はあるが未通電**（`staged/` が存在しない） |
| 新規イベントの登録 | 掲示物レポート（`docs/official-notice-field-report-operations.md`） | **通電済み**・2026-07-26に3件の実績あり |
| 中止・順延など状態更新 | 上記1つ目に `cancel` 系の apply_value を追加 | 要拡張 |
| `domain_stage` 行きの118件 | — | **反映先のコードが存在しない**。経路ができるまで受信箱に出さない |

新しく書くのは **X由来候補 → review_inbox アダプタ**（`review_inbox_adapters/x_gap_adapter.py`）
と、4.1の穴埋め候補ビルダー（`build_x_gap_candidates.py`）の2本。ただし上記のとおり
1つ目の経路は通電したことがないので、**「2本書けば終わり」ではなく、既存経路の疎通に
それなりの手当てが要る**と見ておくこと。

既存の `x_news_digest_for_oto.json`（7,235件）は**受信箱の入力にしない**。
`rare_signal_adapter.py` の冒頭コメントが既に
"The machine-generated X digest is intentionally not an inbox source" と宣言している方針を
維持する。ダイジェストは調査用の参照資料として残す。

### 4.3 人間レビュー — 3レーンに分け、内田さんの枠を1日3件に固定

**レーン1 — 完全自動（人が触らない）**

次の3条件を**すべて**満たすものだけ:
- 発信元が `x_official_source_accounts.json` の公式アカウント
- 既存 occurrence の属性を埋めるだけ（日付確定・時刻・中止／順延）
- 既存の値と矛盾しない（既に値がある欄を上書きしない）

新規登録は絶対に入れない。間違えても後から直せる範囲に限る、という線引き。
反映は既存の `apply_change_requests` を通し、日次メールに反映内容を記録する。

**レーン2 — ことが決める（内田さんは見ない）**

新規イベントの登録、ポスターの読み取り、非公式アカウント由来の日付情報。
ことが判断して apply し、結果を日次メールに「今日入れた分」として1行ずつ載せる。
事後に取り消せる形にしておけば事前確認は要らない。1日30件が上限。

**レーン3 — 内田さんの判断（1日3件まで）**

ことが判断つかない、公開済み情報と矛盾する、盆踊りかどうか怪しい、のいずれか。
`review_inbox_items` に `time_scope=future` の pending として積み、
**上位3件だけをレビューコンソールに出す**。超過分は翌日へ回す。

受け皿は `review_inbox` に一本化する。既にRDBネイティブでv2スキーマも入っており、
器としては十分。

### 4.4 止めるもの

以下は「作り続けても誰も読まない」ため、日次生成を止めるか、上記3レーンのいずれかに
接続する。判断はおとに委ねるが、**どちらでもないものは残さない**方針を明示する。

- `data/retrospective_harvest_candidates.json`（3,629件・日次再生成）
- `data/weekly_harvest_candidates.json` / `weekly_harvest_review_candidates.json`
- `data/rare_signal_candidates.json` / `rare_signal_registration_candidates.json`
- `data/event_date_update_candidates.json`
- その他 `collect.yml` が生成する候補系JSONのうち、レーンに接続しないもの

あわせて、**反映先のコードが存在しない `domain_stage` 行きの種別（YouTube証拠99件・
用語/曲/会場候補19件）は、経路ができるまで受信箱に出さない**。押しても何も起きない
カードが並んでいると、受信箱そのものが信用されなくなる。

## 5. 実装項目と受け入れ条件

### P0: 探索窓の未来走行を止める（最優先・シーズン中）

- `_advance_event_evidence_state()` に「窓の終端が現在（JST）を越えない」上限を入れる。
  現在に追いついたら前進を止め、直近14日を繰り返し走査する挙動にする。
- `data/x_event_evidence_state.json` の現在窓を、実データのある位置へ戻す。
  最後に成果のあった窓が `2026-07-07 → 2026-07-21` なので、そこから再開する。
- 受け入れ条件: 次回 collect 実行で `[event-queue] イベント候補なし` が出ず、
  `evidence_detected > 0` になること。回帰テストで「窓が未来へ進まない」ことを固定する。

### P1: 穴埋め駆動の候補ビルダー

- `build_x_gap_candidates.py` を新設。master RDB の穴（4.1の1〜4）を列挙し、
  voices から証拠を引き当て、**上限30件**の候補JSONを出す。
- 受け入れ条件: 出力が常に30件以下。開催日未確定イベントに一致する候補が優先して
  上位に来る。alias 経由の突合が効いていること（英語名・別名で拾えること）。

### P2: X → review_inbox アダプタ

- `review_inbox_adapters/x_gap_adapter.py` を新設。P1の出力を
  `source_adapter.py` の契約（`docs/review-inbox-source-adapter-contract.md`）に従って
  受信箱アイテムへ変換する。`time_scope=future` を明示的に付ける（現状 future は
  ゼロなので、ここが最初の future アイテムになる）。
- **あわせて受信箱から先を通電させる。** `apply_review_console_decisions.py --write` →
  `build_change_requests_from_review_inbox.py` → `apply_change_requests --dry-run` を
  実際に1件通す。`data/review_console/staged/` はまだ存在しないので、ここで初めて生成される。
  ここが未知数なので、工数はこのP2に厚めに見ておくこと。
- カード横に「その名前でRDBをあいまい検索した候補」を出す（1.4b-4）。完全一致に頼らない。
- 受け入れ条件: `kind + source_id + source_key` が安定し、同じ投稿が翌日再投入されない。
  **X由来の1件が、受信箱から dry-run の change_request まで実際に到達すること**（通電確認）。
  既存の shadow/parity の枠組みで検証してから本番 dual-write へ移す。

### P3: 3レーンの実装

- レーン1の自動反映条件を `collect.py` またはレーン専用スクリプトに実装。
  **公式アカウント × 既存 occurrence の属性のみ × 非上書き** の3条件を満たさないものは
  必ずレーン2以降へ落ちること。
- レビューコンソールの表示を「レーン3の上位3件」に制限する。
- 受け入れ条件: レーン1が新規イベントを作らないこと（テストで固定）。
  コンソールに4件目以降が出ないこと。

### P4: 滞留分の精算

- イベント候補キュー2,460件のうち50点超34件を、P1の穴埋め基準で再評価して処理する。
  残り2,426件は「未確認」のまま放置せず、アーカイブ状態へ落とす。
- `review_inbox_items` の pending 406件を、処理するか一括クローズするか決めて精算する。
- ポスターキュー未読2,214件は、P1の絞り込みを適用して30件/日へ落とす。

### P5: 候補ファイルの停止

- 4.4の各ファイルについて、レーン接続 or 生成停止を決め、`collect.yml` を整理する。
- 受け入れ条件: `collect.yml` が生成する候補系JSONが、すべて3レーンのいずれかに
  接続していること。接続先を説明できないものが残らないこと。
