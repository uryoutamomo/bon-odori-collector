盆助 全体地図

盆助（ぼんすけ、https://bonsuke.jp ）は、東京23区の盆踊りの開催情報を自動で集めて公開する仕組みである。 Claude や Codex が動いていない時間も GitHub Actions が自律的に走り、収集・判断・公開までが毎日回る。

このページは最初に開く1枚で、目的は「いまどこの話をしているのか」を決めることだけ。 詳しいことは何も書かない。当たりをつけたら L1 へ降りる。

  • 仕様書そのものの読み方・書き方は SPEC-GUIDE にある。仕様書を書き足す前に必ず読む。
  • ファイルを触るのが先に決まっているなら、このページではなく index.json の逆引きを使う。

何を解いている仕組みか

盆踊りの開催情報は、驚くほどどこにもまとまっていない。町会の掲示板、神社の貼り紙、区の広報、 主催者のX投稿にばらばらに存在し、多くは開催の数週間前にならないと出てこない。しかも毎年ほぼ同じ時期に、 ほぼ同じ場所で開かれるのに、その「例年こうだ」という知識もどこにも書かれていない。

盆助は、この散らばった断片を機械が集め、確からしさを判断し、 確定した情報と、まだ推測でしかない情報を区別したまま公開する。区別を保つことが設計の中心にある。 「たぶん去年と同じ日だろう」を確定情報として出してしまえば、人を存在しない盆踊りへ歩かせることになるからだ。

人のレビュー運用サブシステム

上位は全体地図。下流はマスタ。

この工程は何のためにあるか

機械が決められないものを、人が裁定する工程である。 断片から「この投稿はこのイベントの告知だ」「この会場はここだ」と決めきれないものが必ず残るので、 それを受信箱に積み、レビューコンソールで人が判断し、決定をマスタへ渡す。

盆助全体の律速はここにある。 集めることでも判断することでもなく、 人が裁定を下す速度が全体の速度を決めている。実際、精度が悪いように見える場面を追いかけると、 判定アルゴリズムではなく人のレビューが詰まっていることのほうが多い。 「精度が悪い」と感じたら、まず止まっている工程を探すのが正しい順序になる。

もうひとつ、この工程には性質上の難しさがある。人の判断は繰り返せない。 同じ画面をもう一度開いて同じ操作をしたときに、決定が二重に適用されたり、 裁定した相手が別のイベントにすり替わっていたりすると、人は自分の判断を信用できなくなる。 だから設計の重心は「詰まらせないこと」と「決定を取り違えないこと」の2つに置かれている。

マスタ（Master RDB）サブシステム

上位は全体地図。下流は公開サブシステム。書き方の決まりは SPEC-GUIDE。

この工程は何のためにあるか

「確定した事実」の正本を持つ工程である。イベント系列、開催回、会場、曲目、そして それぞれの根拠が SQLite（data/bon_odori_master.sqlite）に入っていて、公開もメールもここから作られる。

この工程の難しさは、保存することではなく 確定と推測を混ぜないことにある。 盆踊りは毎年ほぼ同じ時期・同じ場所で開かれるので、「去年8月第2土曜だったから今年もそうだろう」は だいたい当たる。だが当たることと確定していることは違う。過去実績をそのまま今年の開催日として 書き込んでしまえば、RDBは「確定情報」の顔をしたまま推測を抱え込み、下流のどこにもそれを見分ける手段が無くなる。

したがってこの工程の設計は、書き込み口を絞ることに集中している。 何でも書ける汎用の更新機能をあえて持たず、変更の種類を有限にし、種類ごとに必要な根拠を強制する。

主要な流れ

日次では、S3から取得 → 監査 → 各種同期 → 変更があれば publish、という順に進む。

  1. 取得 — master_db_s3_artifact.py fetch --overwrite。チェックサム検証つき（INV-MST-006）。
  2. 監査 — audit_master_rdb.py。取得直後に一度、書き込み後にもう一度走る。
  3. 状態軸の同期 — event_model/state_axes_migration.py 系。開催回の状態を正規化する。
  4. 終了した開催回の遷移 — transition_ended_occurrences.py。過ぎた開催回を「終了」へ落とす。 これが動かないと、終わった行事が公開面に「開催予定」として残る。
  5. 変更リクエストの適用 — report_apply/apply_change_requests.py。dry-run → レビュー → apply → 再検証（INV-MST-003）。
  6. publish — 書き込みが起きたときだけ。CAS（INV-MST-004）とスキーマ退行検査（INV-MST-005）を通る。

凍結という仕組みもある。 master_rdb_freeze_policy.py は、移行中の生成物を一時的に止めるための スイッチで、日次workflowが is-frozen <group> の終了コードで分岐している。 凍結されたグループの生成物は作られないので、「出力が消えた」と思ったらまずここを疑う。

ひとつは、公開が「外に出てしまうと取り消せない」種類の操作だからだ。内部データがおかしくても直せばいいが、 終わった盆踊りを「開催予定」として出してしまえば、それを見た人が実際に会場へ足を運んでしまう。

もうひとつは、公開JSONが RDBの素直な射影ではないことだ。RDBから出した生データに対して、 過去実績の付与・表示段の決定・季節ヒント・日付予測といった後処理が何段も重なる。 つまり「RDBを直したのに公開が変わらない」「RDBは正しいのに公開だけ壊れる」が普通に起きる構造になっている。 公開の不具合を調べるとき、RDBだけ見て納得してはいけないのはこのためである。

配信サブシステム（メール）

上位は全体地図。日刊メールと金曜週報を内田さんへ届ける工程。

この工程は何のためにあるか

集めた情報を、毎日メールとして届ける工程である。盆助のサイトは「調べに行く」ものだが、 メールは「向こうから来る」ので、日々の変化に気づくための主要な経路になっている。

この工程が他と決定的に違うのは、送ってしまうと取り消せないことだ。 RDBが壊れても直せるし、公開JSONが変でも作り直せる。だがメールは配送された時点で終わりで、 間違いに気づいてから止める手段が無い。したがって設計は、内容の正しさより先に 「二重に送らない」「黙って送り損ねない」の2点に寄っている。

構造としては、本文を作る側（こと）と送る側（GitHub Actions）を分けてある。 ことが data/pending_mail.json を書いてコミットし、Actions がそれを見つけて送る。 ローカルから直接SMTPを叩かないのは、送信の記録がリポジトリの履歴に必ず残るようにするためである。

この工程は何のためにあるか

盆助が公開しているのは開催日時と場所だけではない。その盆踊りで何が踊られるか、つまり曲目も出している。 これは盆踊りを探す人にとって、日付と同じくらい行くかどうかを左右する情報である。 炭坑節と東京音頭だけの会と、地元の音頭が10曲並ぶ会は、まったく別の体験だからだ。

ところが曲目は、開催情報以上にどこにも書かれていない。区の広報にもチラシにも曲名までは載らないことが多く、 実際に踊った人のX投稿、YouTubeの概要欄に貼られたセットリスト、会場に張り出された曲目表の写真といった、 断片的で形式のばらばらな痕跡からしか復元できない。しかも同じ曲が「東京音頭」「大東京音頭」「東京五輪音頭」のように 似た名前で並ぶので、取り違えると別の曲を踊ることになってしまう。

そこでこの工程は、次の3つを引き受けている。

  1. ばらばらの文章・動画・写真から、曲名らしき文字列を取り出す。
  2. その文字列が本当に曲名か、どの曲かを、蓄積した曲マスタに照らして決める。決めきれないものは人へ回す。
  3. どの開催回で踊られる（踊られた）かを結びつけ、確からしさの出どころを添えたまま公開する。

3番目が肝心である。曲目には「今年の告知に載っていた」「実際に踊られたのを見た」「去年踊っていたから今年もたぶん踊る」の 3種類がどうしても混ざる。これを区別せずに並べると、去年の話を今年の予定として読ませることになる。 盆助全体の設計思想である「確定と推測を混ぜない」が、曲目でも同じ形で効いている。

主要な流れ

最初に、なぜこれだけドメインで切ってあるかを書いておく。曲目は収集から公開までの全工程を縦に貫いており、 どの工程のL1へ入れても話が半分になる。抽出だけを判断L1へ置けば「なぜ抑制リストが完全一致なのか」が説明できず、 公開の並べ方だけを公開L1へ置けば「その根拠ラベルはどこで決まったのか」が消える。 曲目は工程ではなく一本のパイプラインとして読まないと理解できないので、縦で切ってある。 同じ理由で、export_public_events.py そのものは公開L1が owns したままにしてある（1ファイルを2つの仕様が持てないため）。

1. 候補を拾う（毎日）

日次の collect.yml（毎日 約15:13 JST）で動くのは次の3つである。

  • build_event_song_candidates.py — 公開済みイベントの本文へ extract_song_candidates() をかけ、 レビュー用の曲候補キューを作り直す。抽出はわざと甘くしてある。落としたものは復元できないが、 余計に拾ったものは人が捨てられるからである。
  • build_song_ocr_queue.py — data/voices.json から、曲目表の写真が付いていそうな投稿を選ぶ。 画像の中の曲目は文章からは取れないので、OCRへ回す入口をここで作る。
  • triage_weekly_song_candidates.py --dry-run — 週次収穫が拾った用語候補のうち 曲候補 の行を仕分ける。

抽出そのものは song_processing/bon_odori_songs.py にある。同じモジュールに2つの入口があり、性格が違う。 extract_song_hints() は公開本文からそのまま出してよい程度に絞った抽出で、 extract_song_candidates() はレビュー前提でもっと広く拾う抽出である。混ぜて使ってはいけない。

2. どの曲かを決める（毎日）

classify_candidate() が、候補の文字列を4つの行き先へ振り分ける。 先に手書きの対応表（CANONICAL_MAP / NOISE_EXACT / AMBIGUOUS_TERMS）を見て、 それで決まらなければ SongCatalog（RDBの songs / song_aliases）へ問い合わせる。

台帳が形の判定より優先される。ふるさと音頭 のように「と」が入っていて形の判定では文章に見える曲でも、 台帳に検証済みで載っていれば正規曲名へ解決する。逆に形が完璧でも台帳が 候補 のままならレビューへ回す（INV-SNG-003）。

f517fa8 時点で日次に記録されている仕分け結果は、曲候補207件・直接採用134件・ノイズ68件・要レビュー5件である。

3. 人が裁定する

決めきれなかったものは data/weekly_song_candidates_review.json に出て、 日次の低優先レーンからレビュー受信箱へ入る（--source daily_song_candidate=...）。 裁定の結果は song_candidate_finite_actions.py が定める有限の行動 （register_song / add_song_alias / reject_song / hold）に変換され、 apply_song_candidate_finite_actions.py がマスタへ書く。 レビューされていないものが暗黙に採用されることはなく、決まっていなければ hold になる。

4. 開催回へ結びつけ、確からしさを計算する（手動）

occurrence_songs に曲を積み、確率を計算するのが calibrate_song_probabilities_rdb.py（今年の直接証拠）と inherit_song_probabilities_rdb.py（前年からの継承）である。 この2本はどのworkflowからも呼ばれていない。 内田さんかAIが必要なときに手で回す。 つまり公開されている曲の確率は、最後に誰かがこれを実行した時点のもので、毎日は更新されない。

5. 公開へ渡す（毎日）

export_public_events.py が開催回ごとに occurrence_songs を読み、本文からの抽出結果とマージして公開形にする。 RDBに1行でも曲があれば、RDB側が正として扱う。凍結された旧JSON（data/song_occurrences.json）は RDBに曲が無い開催回のときだけ使う。順序が逆だと、凍結されて古いままの確率がRDBの計算結果を毎日上書きしてしまう。

f517fa8 時点の実データでは、公開379件のうち曲目が付いているのは55件、曲の延べ数は642件（異なり375曲）である。 根拠の内訳は実測346・今年告知9・今年ヒント73・過去実績191、そして本文抽出だけで根拠ラベルの無いものが23件ある。

年次と同定

event_series.series_key は年を含まない系列の一意キーで、表示名も年を原則含めない。event_occurrences は series_id、event_year、occurrence_sequence の一意組で年ごとの開催回を表す。複数回開催にも occurrence_sequence で対応する。会場は系列の通常会場と開催回の実会場を別々に持つ。

inherited_from_occurrence_id は過去年との由来を記録する外部キーで、過去年情報を今年の確定情報へコピーする印ではない。event_series_aliases（25行）は別名を少数の明示的な同定規則として持つ表であり、名称の曖昧な自動併合をする表ではない。

確定・推測・観測の境界

occurrence_dates は特定の occurrence_id に結び、日付・根拠種別・確信度・根拠IDを持つ。対して predicted_occurrence_dates は historical_promotion_candidates を起点に、予測年、根拠方式、スコア、適用状態を保持する候補である。予測の target_occurrence_id は任意で、系列だけに結び付く候補を許す。

開催回の current_event_state と date_certainty_tier も別軸である。前者は predicted/announced/confirmed/ended/cancelled、後者は confirmed/rule_predicted/historical_slide/season_hint/historical_reference を表す。したがって過去年の根拠は将来開催の確定日へ昇格しない。これはL1-masterの「今年の確定には今年の根拠」のデータ上の受け皿である。

根拠の参照方法

evidence_items はプラットフォーム、種別、URL、公開・観測時刻、原文抜粋、原payloadを一度保存する。根拠は開催回へ occurrence_evidence_links（対象とリンク状態・信頼度付き）、曲へ occurrence_song_evidence_links を通して多対多で結ぶ。同じ根拠を複数の開催回・曲へ引用でき、根拠本文をコピーしない。

未同定の外部入力は observed_occurrences と observed_occurrence_songs に残し、matched_* と match_status で確定側への対応の有無を明示する。観測を消して確定表へ直接入れると、後で同定規則を直せず、根拠の出所も失われる。

仕様書の仕様（このフォルダの読み方・書き方）

盆助はソースだけで約14万行あり、日次パイプラインは40近い工程が数珠つなぎになっている。 この規模になると「ソースを読めば分かる」は成り立たない。読めば分かるのは*その1ファイルが何をしているか*だけで、 それを変えると他のどこが壊れるかは、どこにも書いていないからだ。

実際にこれまで、小さな修正が全体を壊す事故が何度も起きている。原因はほぼ常に同じで、 直した本人（人でもAIでも）が「この値が下流でこう使われている」という前提を知らないまま触ってしまう、というものだった。

この docs/spec/ は、その前提を書き留めておく場所である。目的は2つ。

  1. 内田さんが全体を見渡しながら、細かい修正の指示を出せるようにする。 どこを触る話なのか、それは何に影響するのかを、ソースを読まずに把握できる状態にする。
  2. AIが修正前に「壊してはいけないもの」を知れるようにする。 触るファイルから逆引きして、関係する仕様と不変条件に必ず行き着けるようにする。

仕様書は4段。上ほど「なぜ・何を」、下ほど「どうやって」に寄る。 上の層は下の層の要約ではない。層ごとに答える問いが違う。ここを混ぜると、どの層も中途半端になる。

owns は排他にする。1つのソースファイルを2つの仕様セクションが owns してはいけない。 どちらを直せばいいのか分からなくなるからだ（index.json の生成時に検査して落とす）。 複数から参照したいだけなら depends_on を使う。 owns は、人が直接変更することがあるソース・成果物を指す。index.json や生成HTMLなど、誰も直接編集しない純粋な生成物は owns しない。 一方で公開JSONのように機械も人も変更しうる成果物は、逆引きで不変条件を示す価値があるため owns してよい。 鮮度指標は自動コミットを数えず、人による変更だけを数える。これにより、成果物の自動更新で見直し時期を誤って示さない。

updated_for は「この記述を最後に実態と突き合わせたコミット」を書く。 更新した日付ではなくコミットハッシュにしているのは、そこから owns 配下の差分を機械的に数えて、 「この仕様は何コミット分の変更を見ていないか」＝鮮度を測れるようにするため。

本文の型

L1 の本文は次の見出しを必ずこの順で持つ。順番を揃えるのは、AIが部分読みしても迷子にならないようにするため。

  1. この工程は何のためにあるか — 1〜3段落。目的と、無かったら何が困るか。
  2. 入力と出力 — 何を受け取り、何を出すか。ファイルパス／テーブル名／外部APIを具体名で。
  3. 不変条件 — 後述の書式。ここがこの仕様書の中心。
  4. 主要な流れ — 実際の処理順。各段でどのファイルが動くかを名指しする。
  5. 依存と影響 — 上流が壊れたとき何が起きるか、下流に何を渡しているか。
  6. 壊れたときの症状 — 「公開件数が急に減る」「区ごとの偏りが出る」など、外から見える形で書く。 これは事故ったときの逆引きに効く。症状から原因の当たりをつけられる。
  7. 未解決・注意点 — 分かっているが直っていないこと。

不変条件（INV）の書き方

不変条件は「常に成り立っていなければならないこと」で、破ると全体が壊れる約束を指す。 仕様書の中で最も重要な部分なので、書式を固定する。

### INV-COL-001 ノイズ判定の投稿は voices.json に入れない

- **内容**: X収集で除外語にヒットした投稿は、`data/voices.json` へ書き出さない。
- **なぜ**: voices は公開サイトの「声」欄と週報の入力を兼ねている。ノイズが混ざると
  公開面に無関係な投稿が出るうえ、週報の分量設定も崩れる。
- **破れたときの症状**: 公開サイトの声欄に盆踊りと無関係な投稿が並ぶ／週報が異常に長くなる。
- **守っているコード**: `collect.py` の仕分け処理
- **守っているテスト**: `tests/test_x_collection.py::test_noise_excluded_from_voices`

ルールは3つ。

  • IDは INV-<サブシステム3文字>-<連番>。 一度振ったIDは意味を変えない。不要になったら本文に「廃止」と書いて残す。 IDが使い回されると、過去のPRコメントやメモが別のことを指すようになってしまう。
  • 必ずテストを1件以上紐づける。 テストの無い不変条件は、破れても誰も気づかないので守られていないのと同じ。 紐づけるテストは「修正を外したら落ちる」ものであること（テストが全部通ることは合格の根拠にならない）。 まだテストが無い場合は 守っているテスト: **なし（要追加）** と正直に書く。これは負債として可視化する。 引用は tests/x.py::test_y でも tests/x.py::Class::test_y でもよい。 unittest.TestCase で書いたテストはクラス名まで書く（そうしないと pytest から選び出せない）。
  • 症状は外から見える形で書く。 「内部状態が不整合になる」ではなく「公開件数が減る」「終わった行事が開催予定のまま残る」。 内田さんが異変に気づいたとき、症状から仕様を引けるようにするため。
検査の限界を知っておくこと。 spec_index.py check が見るのは、 引用されたテスト関数が実在するかどうかだけである。 そのテストがその不変条件を本当に守っているかは、機械には判定できない。 そのテストがその不変条件を本当に守っているかも、引用先のコードが実際に使われているかも、機械には判定できない。 引用テストの妥当性は、レビューする人が中身を読んで確かめるしかない。 逆に言えば、check が緑であることは「テストが実在する」以上の意味を持たない。

2026-08-13 に、同じ形の穴を1日で2回踏んだ。どちらも check は緑だった。

  • 無関係なテストを引く（INV-SCH-003）。引用先は実在する良いテストだったが、 検査していたのは別のことだった。
  • 使われないコードを引く（同じく INV-SCH-003）。仕様書が実在しない関数を書いていたため、 その関数を新しく作ってテストを付けた。関数もテストも実在し、テストも通る。 しかしその関数は誰からも呼ばれていなかったので、実際にスキーマを変える経路が 記録を止めても何も起きない。

2つめのほうが見つけにくい。テストを読んでも正しく見えるからで、 気づくには引用先のコードを誰が呼んでいるかを検索するしかない。 レビューでは grep を1回かけて、実経路から呼ばれていることを確かめる。

もうひとつ、検査では見えない構造上の穴がある。不変条件を書いた仕様と、 それを守っているコードを owns している仕様が別々のとき、逆引きにその不変条件は出てこない。 owns は排他なので、1つのファイルが複数の関心事を抱えていると必ずこれが起きる。 実例は export_public_events.py で、ファイルは公開L1のものだが、曲の抑制と根拠ラベルの約束は 曲目L1（INV-SNG-001 / INV-SNG-002）にある。この形になったら、owns している側の本文に 「この関数を触るときはあちらを見る」と明示的に書いておくこと。 逆引きが片道になったままだと、 仕様書がある領域なのに警告が出ない状態になり、最初から無いより危ない。

更新のタイミング

仕様書は書いた瞬間から古くなる。放っておくと必ず腐るので、更新を人の善意に頼らない。 まず大原則をひとつ置き、そのうえで4つの契機を、自動化の強さを変えて設ける。

0. コードを変えたら、同じPRで仕様書も直す（大原則・2026-08-13 内田さん指示）

追加・修正・削除のどれであっても、docs/spec/ を同じPRの中で直す。 別PRに切り出さない。 後回しにすると必ず忘れられ、仕様書は現実を写さない飾りになる。そうなった仕様書は、 無いよりも危ない。読んだ人が「確認済みの情報だ」と信じてしまうぶんだけ害が大きいからだ。

具体的にすることは4つ。

  • 作業を始める前に spec_index.py impact --files <path>... を引き、 触るファイルがどの仕様に属し、どの不変条件に関わるのかを見る。
  • 挙動を変えたら、その仕様の本文と updated_for を更新する。
  • 守るべき約束が増えた・変わった・不要になったなら ### INV-xxx を追加・修正・廃止する。
  • ファイルを消す・移動する・分割するときは owns を必ず直す。 減らしたら、その場で impact を引いて意図どおりか確かめる。

最後のひとつは実際に事故った。2026-08-13、owns を縮める調整の巻き添えで master_rdb/s3_artifact.py が抜け落ち、スキーマ退行事故の再発防止が書いてあるファイルを 触っても警告が出ない状態になった。仕様書があるのに逆引きから消えるのは、 「未記述だから気にしなくていい」と誤解される点で、最初から無いより悪い。

1. PR を作る・更新するとき — 影響範囲を知らせる（自動・情報提供）

変更されたファイルから index.json を逆引きし、 関係する仕様セクションと不変条件をPRにコメントする。

これがこの仕組みの主目的である。「小さい修正のつもりが全体を壊す」は、 触っている本人が影響範囲を知らないから起きる。PRの時点で 「この変更は INV-PUB-002（公開件数の急減を防ぐ）に触れます」と出れば、その場で気づける。

影響コメントではCIを落とさない。 落とすと「仕様も直しました」と形式的に埋めるだけの作業になり、 肝心の警告が読まれなくなる。情報を出して、直すかどうかの判断は人とAIに委ねる。

ただし同じPRの中で、次に述べる機械的な整合性検査は落とす。こちらは判断の余地が無い事実だけを見るので、 埋め作業になりようがない。

2. 同じくPRのとき — 機械的な整合性を守る（自動・失敗させる）

  • owns が指すファイルが実在するか（消えたファイルを指したままになっていないか）
  • 1ファイルを2つの仕様が owns していないか
  • INV が指すテストが実在するか
  • front matter の invariants と本文の INV 見出しが一致しているか
  • 仕様ファイル間のリンク切れ

いずれも人の判断が要らない事実なので、自動で守れる。逆に「記述の内容が実態と合っているか」はここでは見ない。 機械には見られないからで、それは4番目の契機で人とAIが担う。

検査を merge 後ではなくPR時に置くのは、merge してから落ちても直す先が main になってしまい、手戻りが大きいため。

2-b. main へ push されたとき — 索引を作り直す（自動）

index.json と、閲覧用の docs/spec/site/index.html を再生成して自動コミットする。鮮度指標（updated_for からの差分）はこのとき更新される。 再生成を main 側に寄せるのは、PRごとに索引が競合して無駄な衝突が起きるのを避けるため。 HTMLは scripts/spec_html.py が索引とMarkdownから生成する。手書きで直してはいけない。

3. 本番リリース（公開サイトへの反映）のとき — 稼働している姿を刻む（自動）

L0 の「いま動いている姿」の節に、その時点の公開件数・稼働workflow・最終デプロイを記録する。 仕様書と実際に動いているものが同じ世代であることを示すため。

4. 一区切りついたとき — 記述の中身を見直す（AIが実施）

上の3つはどれも形式しか守れない。「書いてあることが実態と合っているか」は読んで確かめるしかない。 そこで、次のどれかに当たったら、こと（Claude Code）が該当L1を実態と突き合わせて本文を直し、updated_for を更新する。

  • あるテーマのPR群が終わったとき（例：X盆踊ラー再評価の一連が main に入り切った）
  • 事故が起きて原因が判明したとき（症状と不変条件を必ず追記する。同じ事故を二度繰り返さないための蓄積）
  • index.json の鮮度指標で、updated_for から一定以上の差分が積もった仕様が出たとき

3番目を数値で持つことで、「そろそろ見直しどき」を人が覚えていなくてよくなる。

5. ずれを見つけたとき — その場で直す（発見次第・2026-08-13 内田さん指示）

上の0〜4をすべて守っても、仕様書と実態はずれる。人もAIも見落とすし、急ぎの修正では手が回らないこともある。 だからずれを「あってはならないもの」として扱わない。 前提として織り込み、見つけ次第直す運用にする。

ずれていること自体は失敗ではない。見つけたのに直さず素通りすることが失敗である。

  • 作業中に「記述が実態と違う」と気づいたら、その場で直す。 別タスクへ切り出したり、内田さんへ確認を求めたりしなくてよい。
  • 直すのは気づいた範囲だけでよい。 ついでに周辺を全部点検し直す必要はない。 完璧を求めると誰も手をつけなくなり、かえってずれが残る。
  • 実装を読んでも正解が分からない場合は、推測で書き換えない。 該当箇所に「未確認」と明記して残す。間違った記述より、確認していないと分かる記述のほうがよい。

この5番目があることで、0〜4を厳密に運用しきれなくても仕組みが壊れない。 完璧な同期ではなく、ずれが見つかるたびに縮む状態を目指している。

網羅していないことを隠さない

最初から全ソースを仕様化することはできない。668ファイルあるので当然そうなる。 なので index.json は、どの仕様にも owns されていないファイルを「未記述」として数え、L0 に出す。

網羅率が低いこと自体は問題ではない。問題なのは、網羅していないのに網羅しているように見えることだ。 「この領域はまだ仕様書が無いので、ソースを直接読む必要がある」と分かれば、AIも人も正しく振る舞える。

この仕様書を書くときの姿勢

  • ソースを見て書く。記憶で書かない。 実装を確認せずに書いた仕様は、実態と違ううえに、 読んだ人が確認済みだと信じてしまうぶん害が大きい。
  • 確認していないことは「未確認」と書く。 埋めるために推測を書かない。
  • なぜそうなっているかを残す。 「何をしているか」はソースを読めば分かるが、 「なぜその判断をしたか」はソースから復元できない。仕様書が本当に価値を持つのはここ。
  • 失敗の記録を消さない。 一度壊れた箇所は、また壊れる。事故は不変条件として残す。
