# 仕様書の仕様（このフォルダの読み方・書き方）

盆助はソースだけで約14万行あり、日次パイプラインは40近い工程が数珠つなぎになっている。
この規模になると「ソースを読めば分かる」は成り立たない。読めば分かるのは*その1ファイルが何をしているか*だけで、
**それを変えると他のどこが壊れるか**は、どこにも書いていないからだ。

実際にこれまで、小さな修正が全体を壊す事故が何度も起きている。原因はほぼ常に同じで、
直した本人（人でもAIでも）が「この値が下流でこう使われている」という前提を知らないまま触ってしまう、というものだった。

この `docs/spec/` は、その前提を書き留めておく場所である。目的は2つ。

1. **内田さんが全体を見渡しながら、細かい修正の指示を出せるようにする。**
   どこを触る話なのか、それは何に影響するのかを、ソースを読まずに把握できる状態にする。
2. **AIが修正前に「壊してはいけないもの」を知れるようにする。**
   触るファイルから逆引きして、関係する仕様と不変条件に必ず行き着けるようにする。

## 階層の考え方

仕様書は4段。上ほど「なぜ・何を」、下ほど「どうやって」に寄る。
**上の層は下の層の要約ではない。**層ごとに答える問いが違う。ここを混ぜると、どの層も中途半端になる。

| 層 | 場所 | 答える問い | 読む人 | 分量の目安 |
|---|---|---|---|---|
| **L0** | `docs/spec/README.md` | 盆助とは何をする仕組みか。どこを見ればいいか | 内田さん・初見のAI | 1画面 |
| **L1** | `docs/spec/L1/*.md` | このサブシステムは何に責任を持ち、何を壊してはいけないか | 修正の方針を決める人 | 各200〜400行 |
| **L2** | `docs/spec/L2/*.md` | 工程どうしが受け渡すデータの正確な形は何か | 実装するAI | 契約ごと |
| **L3** | ソースコード | 実際にどう動くか | 実装するAI | — |

L3（ソース）は仕様書に写さない。写した瞬間に必ず古くなるからだ。
代わりに L1・L2 から**ファイルパスと関数名で名指しする**。仕様書の役割は説明の複製ではなく、
「この話の実物はここにある」という道案内と、「ここは動かすな」という警告の2つに絞る。

### 縦に降りる道と、横に辿る道

読み方は2通りある。

- **縦に降りる（分からないことを調べる）**: L0 の地図でどのサブシステムの話か当たりをつけ、L1 でその責務と不変条件を読み、
  L2 でデータの形を確認し、L1/L2 が名指ししているソースへ飛ぶ。
- **横から入る（触るファイルが先に決まっている）**: `docs/spec/index.json` の逆引きで、
  そのファイルを `owns` している仕様セクションと、紐づく不変条件を引く。**修正前に必ずこちらを通る。**

後者があることが、この仕組みの肝である。「ファイルを触る → 関係する不変条件が出てくる」経路が無いと、
仕様書は書かれるだけで参照されない資料になる。

## ファイルの書式

すべての仕様ファイルは YAML front matter で始める。ここが機械可読部分で、`index.json` の生成元になる。

```yaml
---
id: L1-collection            # 一意。層のプレフィクス + 短い名前
layer: L1                    # L0 / L1 / L2 / meta
title: 収集サブシステム
owns:                        # このセクションが仕様として責任を持つソース（glob可）
  - collect.py
  - collection_support/**
depends_on:                  # 上流として依存する仕様セクションのid
  - L1-platform
invariants:                  # このセクションが定める不変条件のid
  - INV-COL-001
verified_by:                 # 記述が生きている証拠となるテスト
  - tests/test_x_collection.py
updated_for: 6537e7f         # この記述が実態と合っていることを確認したコミット
---
```

`owns` は排他にする。1つのソースファイルを2つの仕様セクションが `owns` してはいけない。
どちらを直せばいいのか分からなくなるからだ（`index.json` の生成時に検査して落とす）。
複数から参照したいだけなら `depends_on` を使う。

`updated_for` は「この記述を最後に実態と突き合わせたコミット」を書く。
更新した日付ではなく**コミットハッシュ**にしているのは、そこから `owns` 配下の差分を機械的に数えて、
「この仕様は何コミット分の変更を見ていないか」＝鮮度を測れるようにするため。

## 本文の型

L1 の本文は次の見出しを必ずこの順で持つ。順番を揃えるのは、AIが部分読みしても迷子にならないようにするため。

1. **この工程は何のためにあるか** — 1〜3段落。目的と、無かったら何が困るか。
2. **入力と出力** — 何を受け取り、何を出すか。ファイルパス／テーブル名／外部APIを具体名で。
3. **不変条件** — 後述の書式。**ここがこの仕様書の中心**。
4. **主要な流れ** — 実際の処理順。各段でどのファイルが動くかを名指しする。
5. **依存と影響** — 上流が壊れたとき何が起きるか、下流に何を渡しているか。
6. **壊れたときの症状** — 「公開件数が急に減る」「区ごとの偏りが出る」など、外から見える形で書く。
   これは事故ったときの逆引きに効く。症状から原因の当たりをつけられる。
7. **未解決・注意点** — 分かっているが直っていないこと。

## 不変条件（INV）の書き方

不変条件は「常に成り立っていなければならないこと」で、破ると全体が壊れる約束を指す。
仕様書の中で最も重要な部分なので、書式を固定する。

```markdown
### INV-COL-001 ノイズ判定の投稿は voices.json に入れない

- **内容**: X収集で除外語にヒットした投稿は、`data/voices.json` へ書き出さない。
- **なぜ**: voices は公開サイトの「声」欄と週報の入力を兼ねている。ノイズが混ざると
  公開面に無関係な投稿が出るうえ、週報の分量設定も崩れる。
- **破れたときの症状**: 公開サイトの声欄に盆踊りと無関係な投稿が並ぶ／週報が異常に長くなる。
- **守っているコード**: `collect.py` の仕分け処理
- **守っているテスト**: `tests/test_x_collection.py::test_noise_excluded_from_voices`
```

ルールは3つ。

- **IDは `INV-<サブシステム3文字>-<連番>`。** 一度振ったIDは意味を変えない。不要になったら本文に「廃止」と書いて残す。
  IDが使い回されると、過去のPRコメントやメモが別のことを指すようになってしまう。
- **必ずテストを1件以上紐づける。** テストの無い不変条件は、破れても誰も気づかないので守られていないのと同じ。
  紐づけるテストは「修正を外したら落ちる」ものであること（テストが全部通ることは合格の根拠にならない）。
  まだテストが無い場合は `守っているテスト: **なし（要追加）**` と正直に書く。これは負債として可視化する。
- **症状は外から見える形で書く。** 「内部状態が不整合になる」ではなく「公開件数が減る」「終わった行事が開催予定のまま残る」。
  内田さんが異変に気づいたとき、症状から仕様を引けるようにするため。

> **検査の限界を知っておくこと。** `spec_index.py check` が見るのは、
> 引用されたテスト関数が**実在するかどうかだけ**である。
> そのテストがその不変条件を本当に守っているかは、機械には判定できない。
> 実際に、無関係なテストを引いた不変条件が check を素通りした事例がある（INV-SCH-003、2026-08-13）。
> **引用テストの妥当性は、レビューする人が中身を読んで確かめるしかない。**
> 逆に言えば、check が緑であることは「テストが実在する」以上の意味を持たない。

## 更新のタイミング

仕様書は書いた瞬間から古くなる。放っておくと必ず腐るので、更新を人の善意に頼らない。
まず大原則をひとつ置き、そのうえで4つの契機を、自動化の強さを変えて設ける。

### 0. コードを変えたら、同じPRで仕様書も直す（大原則・2026-08-13 内田さん指示）

**追加・修正・削除のどれであっても、`docs/spec/` を同じPRの中で直す。** 別PRに切り出さない。
後回しにすると必ず忘れられ、仕様書は現実を写さない飾りになる。そうなった仕様書は、
無いよりも危ない。読んだ人が「確認済みの情報だ」と信じてしまうぶんだけ害が大きいからだ。

具体的にすることは4つ。

- 作業を**始める前**に `spec_index.py impact --files <path>...` を引き、
  触るファイルがどの仕様に属し、どの不変条件に関わるのかを見る。
- 挙動を変えたら、その仕様の本文と `updated_for` を更新する。
- 守るべき約束が増えた・変わった・不要になったなら `### INV-xxx` を追加・修正・廃止する。
- **ファイルを消す・移動する・分割するときは `owns` を必ず直す。**
  減らしたら、その場で `impact` を引いて意図どおりか確かめる。

最後のひとつは実際に事故った。2026-08-13、`owns` を縮める調整の巻き添えで
`master_rdb/s3_artifact.py` が抜け落ち、**スキーマ退行事故の再発防止が書いてあるファイルを
触っても警告が出ない状態**になった。仕様書があるのに逆引きから消えるのは、
「未記述だから気にしなくていい」と誤解される点で、最初から無いより悪い。

### 1. PR を作る・更新するとき — 影響範囲を知らせる（自動・情報提供）

変更されたファイルから `index.json` を逆引きし、
**関係する仕様セクションと不変条件をPRにコメントする。**

これがこの仕組みの主目的である。「小さい修正のつもりが全体を壊す」は、
触っている本人が影響範囲を知らないから起きる。PRの時点で
「この変更は INV-PUB-002（公開件数の急減を防ぐ）に触れます」と出れば、その場で気づける。

**影響コメントではCIを落とさない。** 落とすと「仕様も直しました」と形式的に埋めるだけの作業になり、
肝心の警告が読まれなくなる。情報を出して、直すかどうかの判断は人とAIに委ねる。

ただし同じPRの中で、次に述べる**機械的な整合性検査は落とす**。こちらは判断の余地が無い事実だけを見るので、
埋め作業になりようがない。

### 2. 同じくPRのとき — 機械的な整合性を守る（自動・失敗させる）

- `owns` が指すファイルが実在するか（消えたファイルを指したままになっていないか）
- 1ファイルを2つの仕様が `owns` していないか
- INV が指すテストが実在するか
- front matter の `invariants` と本文の INV 見出しが一致しているか
- 仕様ファイル間のリンク切れ

いずれも人の判断が要らない事実なので、自動で守れる。逆に「記述の内容が実態と合っているか」はここでは見ない。
機械には見られないからで、それは4番目の契機で人とAIが担う。

検査を merge 後ではなくPR時に置くのは、merge してから落ちても直す先が main になってしまい、手戻りが大きいため。

### 2-b. main へ push されたとき — 索引を作り直す（自動）

`index.json` と、閲覧用の `docs/spec/site/index.html` を再生成して自動コミットする。鮮度指標（`updated_for` からの差分）はこのとき更新される。
再生成を main 側に寄せるのは、PRごとに索引が競合して無駄な衝突が起きるのを避けるため。
HTMLは `scripts/spec_html.py` が索引とMarkdownから生成する。手書きで直してはいけない。

### 3. 本番リリース（公開サイトへの反映）のとき — 稼働している姿を刻む（自動）

L0 の「いま動いている姿」の節に、その時点の公開件数・稼働workflow・最終デプロイを記録する。
仕様書と実際に動いているものが同じ世代であることを示すため。

### 4. 一区切りついたとき — 記述の中身を見直す（AIが実施）

上の3つはどれも**形式**しか守れない。「書いてあることが実態と合っているか」は読んで確かめるしかない。
そこで、次のどれかに当たったら、こと（Claude Code）が該当L1を実態と突き合わせて本文を直し、`updated_for` を更新する。

- あるテーマのPR群が終わったとき（例：X盆踊ラー再評価の一連が main に入り切った）
- 事故が起きて原因が判明したとき（**症状と不変条件を必ず追記する**。同じ事故を二度繰り返さないための蓄積）
- `index.json` の鮮度指標で、`updated_for` から一定以上の差分が積もった仕様が出たとき

3番目を数値で持つことで、「そろそろ見直しどき」を人が覚えていなくてよくなる。

### 5. ずれを見つけたとき — その場で直す（発見次第・2026-08-13 内田さん指示）

上の0〜4をすべて守っても、仕様書と実態はずれる。人もAIも見落とすし、急ぎの修正では手が回らないこともある。
だから**ずれを「あってはならないもの」として扱わない。** 前提として織り込み、見つけ次第直す運用にする。

**ずれていること自体は失敗ではない。見つけたのに直さず素通りすることが失敗である。**

- 作業中に「記述が実態と違う」と気づいたら、その場で直す。
  別タスクへ切り出したり、内田さんへ確認を求めたりしなくてよい。
- 直すのは**気づいた範囲だけでよい。** ついでに周辺を全部点検し直す必要はない。
  完璧を求めると誰も手をつけなくなり、かえってずれが残る。
- 実装を読んでも正解が分からない場合は、**推測で書き換えない。**
  該当箇所に「未確認」と明記して残す。間違った記述より、確認していないと分かる記述のほうがよい。

この5番目があることで、0〜4を厳密に運用しきれなくても仕組みが壊れない。
完璧な同期ではなく、**ずれが見つかるたびに縮む**状態を目指している。

## 網羅していないことを隠さない

最初から全ソースを仕様化することはできない。668ファイルあるので当然そうなる。
なので `index.json` は、**どの仕様にも `owns` されていないファイル**を「未記述」として数え、L0 に出す。

網羅率が低いこと自体は問題ではない。問題なのは、網羅していないのに網羅しているように見えることだ。
「この領域はまだ仕様書が無いので、ソースを直接読む必要がある」と分かれば、AIも人も正しく振る舞える。

## この仕様書を書くときの姿勢

- **ソースを見て書く。記憶で書かない。** 実装を確認せずに書いた仕様は、実態と違ううえに、
  読んだ人が確認済みだと信じてしまうぶん害が大きい。
- **確認していないことは「未確認」と書く。** 埋めるために推測を書かない。
- **なぜそうなっているかを残す。** 「何をしているか」はソースを読めば分かるが、
  「なぜその判断をしたか」はソースから復元できない。仕様書が本当に価値を持つのはここ。
- **失敗の記録を消さない。** 一度壊れた箇所は、また壊れる。事故は不変条件として残す。
